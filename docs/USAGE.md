# Руководство пользователя StalBot

Запуск, установка и обзор проекта — в [README](../README.md). Команды выполняются из корня проекта.

Здесь сохранены подробности настроек, режимов, ввода, бюджета и истории. Непроверенные условия отмечены рядом с соответствующей возможностью.

## Каталог и настройки

Кеш NAME включён по умолчанию: LRU на 1000 точных RGB-изображений названий
(ориентировочно 12 МиБ при текущей геометрии). Поле «Кеш NAME, записей» меняет
ёмкость, 0 отключает кеш. Настройка применяется при следующем Старт/Replay;
старые settings.json получают значение 1000 автоматически. CLI принимает
`--name-cache-capacity 0` для сравнения без кеша. Записи и порядок LRU сохраняются
между перезапусками приложения, а счётчики попаданий, промахов и вытеснений сбрасываются
при каждом запуске. Они включают анализ списка и проверку названия в меню.
Цена, количество и решение о покупке всегда вычисляются заново.

Файлы `data/name-cache/cpu.names` и `dml.names` раздельные. Изменения сохраняются
в фоне примерно раз в минуту, в том числе при паузе и неизменном списке; при остановке
и штатном закрытии бот ждёт завершения записи. Загрузка при подготовке OCR оставляет
самые свежие записи в пределах выбранного лимита. Повреждённый/несовместимый файл
пропускается; отсутствие файла нормально для первого запуска. Смена весов,
обработки или поддерживаемого формата автоматически делает старый кеш несовместимым.
В UI видно число записей «с диска» и ошибки дискового кеша; бот продолжает обычный OCR.
0 отключает кеш в памяти, сохраняя прежний файл. CLI: `--name-cache-dir PATH`
для отдельного каталога. Старый кеш, оставшийся только в памяти версии без сохранения,
при первом обновлении перенести нельзя.

«Время сессии» показывает HH:MM:SS от Старт/Replay до завершения, включая подготовку,
паузы и завершение текущей операции. После остановки время остаётся видимым,
при следующем запуске начинается с нуля. Это длительность, а не время активного OCR.

Поле «OCR» переключает **CPU / GPU (DirectML)**. По умолчанию CPU; GPU использует
одну NAME-сессию и технический batch 9 независимо от группы лотов. Числа остаются
на CPU. Переключение применяется при следующем Старт/Replay, закрывает старую модель
и сохраняет её кеш; новый режим загружает свой совместимый файл и прогревается
до захвата экрана. CPU-настройка batch
сохраняется для обратного переключения. При недоступном DirectML запуск останавливается
с ошибкой: выберите CPU. Фактический режим показан в строке подготовки OCR.
CLI: `--ocr-device cpu` или `--ocr-device dml` (в GPU значение `--batch` не меняет batch 9).
Работа GPU вместе с игрой, FPS и задержки ещё требуют пользовательской проверки.

Рабочая база изначально пустая; mock-каталог в неё не добавляется.

После покупки бот распознаёт результат и проверяет/восстанавливает экран перед
следующим Search. Неизвестный результат не разрешает повторный BUY.
На вкладке «Каталог» задайте:

- Полное имя с кавычками, если они входят в название, без суффикса `| +N`.
- Заточку отдельно: `0` — без заточки, `15` — +15, `любая` — признак не влияет на правило.
  Можно вписать диапазон включительно: `0-9`, `10-13`, `14-15`. Одна запись задаёт
  общие цены для всех уровней внутри диапазона. Для оружия, брони и артефактов
  задавайте точное значение или нужный диапазон; непрочитанная заточка в него не входит.
- Цвет: точный цвет имени либо `*`, если редкость не влияет на закупочную цену.
- Закупку и предполагаемую продажу **за одну штуку**; необязательный максимальный стак.

При QTY AMBIGUOUS ограничение стака сейчас проверяется по расчётной единице,
поэтому верхняя граница фактического количества не подтверждается. Это известное
замечание A02 в [аудите](AUDIT_2026-10-20.md).

Сокращённые имена сопоставляются по началу названия среди включённых правил:
покупка разрешена, если подходит ровно одно название и одно правило цвета/заточки.
В каталог вводите полное название либо видимую часть без конечных точек;
полное название предпочтительнее. Неоднозначные имена и пересекающиеся правила пропускаются.
Уникальность префикса среди закупочных правил не гарантирует уникальность предмета в игре.
У сокращённого имени заточка считается 0 по уточнённому игровому правилу.

Поле «Поиск по названию» на вкладке «Каталог» сразу отбирает записи по части имени
без учёта регистра. Поиск меняет только видимый список, все включённые правила
продолжают участвовать в покупке. Старые записи с одиночной заточкой сохраняются;
при следующем запуске структура SQLite обновляется автоматически.

На вкладке «История покупок» есть фильтры по части названия, статусу, датам
и минимальному ROI. Даты выбираются кнопками календаря: есть переход по месяцам,
выбор дня и сброс границы кнопкой `×`. Обе границы включены. Выбранная дата
применяется сразу; при пересечении границ другая граница сдвигается на тот же день.
Кнопки «Вчера», «Сегодня» и «Все даты» задают период одним нажатием, сохраняя
остальные фильтры. Время и календарные дни соответствуют часовому поясу Windows;
в SQLite время по-прежнему сохраняется в UTC.

Для названия и минимального ROI нажмите «Применить фильтры» или Enter; статус
применяется сразу. «Сбросить фильтры» возвращает все статусы и даты.
Нажатие на заголовок любой колонки сортирует записи, повторное — меняет направление;
ROI, прибыль, цена и количество сравниваются как числа. Отображаются **все** записи
по выбранным фильтрам, ограничения в 200 нет.

Над таблицей показаны сумма прогнозной прибыли и число подтверждённых покупок
(SUCCESS с завершённой сверкой баланса). Без фильтров сумма считается за всю неочищенную историю, с фильтрами —
только по подходящим покупкам. Например, «Вчера» показывает прогноз за весь вчерашний
местный день. Комиссия 5% уже включена в прогноз каждой покупки, повторно она
не вычитается. Неуспешные, неопределённые и отмеченные вручную попытки в сумму не
входят. Сумма учитывает сохранённое расчётное количество; QTY AMBIGUOUS по-прежнему
не подтверждает фактическое количество. Скрытые при очистке записи не учитываются.

«Очистить историю покупок» после подтверждения убирает из списка все завершённые
попытки (SUCCESS, UNAVAILABLE, CANCELLED, MANUALLY_REVIEWED), включая скрытые фильтрами.
BUY_SENT, UNKNOWN, INSUFFICIENT и попытки с незавершённой сверкой баланса остаются для проверки и защиты от повторного BUY;
BALANCE_MISMATCH остаётся в истории для аудита, но не блокирует покупки;
UNKNOWN_RECOVERED — для сверки резерва бюджета. Бюджет и прогноз прибыли текущей
сессии не меняются. Для аудита
записи сохраняются в SQLite с отметкой скрытия; файлы диагностики также сохраняются.
Кнопка очистки доступна после остановки бота.

Лимит лота задаётся отдельно, по умолчанию 5 000 000 ₽. При выключенной галочке
«Бюджет из игры» поле «Остаток бюджета» необязательно:
он уменьшается после подтверждённого SUCCESS и сохраняется между запусками.
Пусто — без общего ограничения расходов. При остатке меньше 50 000 ₽ автопокупка
останавливается до нового Search; ровно 50 000 ₽ допускает продолжение.
Проверка действует при запуске, после покупки и резервирования неизвестного результата.
При выключенной галочке это ручной бюджет.
После внешних трат или ручного разбора неизвестной покупки скорректируйте его самостоятельно.

Галочка **«Бюджет из игры»** рядом с остатком включает OCR строки «Счет: … руб.».
По умолчанию выключена; выбор сохраняется, менять его можно между запусками.
При включении бюджет обновляется перед первым Search, после снятия паузы,
после закрытия уведомления SUCCESS/UNAVAILABLE, при UNKNOWN и раз в 60 секунд
между циклами. Наблюдение читает баланс при запуске; Replay и проверка меню
не синхронизируют игровой счёт. Перед стартовой проверкой лимита берётся свежий баланс.
Два одинаковых чтения с интервалом 150 мс подтверждают значение. После UNKNOWN
и UNAVAILABLE дополнительно выдерживаются 700 мс после восстановления аукциона,
чтобы дождаться возврата временного списания. При SUCCESS дополнительной задержки
нет, кроме повторной проверки через 700 мс при расхождении.

Для UNKNOWN точное списание цены означает SUCCESS, отсутствие списания — UNAVAILABLE.
Любое другое изменение, а также несоответствие баланса распознанному уведомлению,
даёт **BALANCE_MISMATCH**, который записывается в журнал без остановки покупок.
Новый баланс сохраняется, исходные расчёты лота остаются в истории, расхождение —
в подробностях `balance_check` и диагностике. Бот продолжает с новым прочитанным
балансом; завершённое расхождение не блокирует покупки и после перезапуска.
Такая попытка не считается подтверждённым SUCCESS и не добавляется к прогнозу прибыли.
Сам баланс не доказывает личность предмета.
Если баланс не читается/нестабилен в течение 2 секунд, запуск останавливается без
догадок и резервирования. Пауза/стоп после BUY сохраняют незавершённую сверку;
она выполняется при продолжении или следующем автозапуске с включённой галочкой.
Выключение галочки не снимает такую блокировку. Старый UNKNOWN без исходного
баланса требует ручного разбора.

Бюджет и история обновляются в UI по событиям сделки, без ожидания остановки.
Числа разделены пробелами по разрядам; в истории дробная часть отбрасывается
только при отображении. Расчёты, фильтры и сортировка сохраняют исходную точность.
OCR баланса проверен офлайн; новые задержки и полный цикл с этой галочкой в игре
ещё требуют проверки. [Результаты и ограничения](../validation/balance-ocr-20261019/README.md).

Лот должен укладываться в лимит лота, закупочную цену × количество и заданный баланс.
Прогноз прибыли = продажа × количество × 0.95 − выкуп; требуется положительная прибыль.
Автоматическая перепродажа не реализована.
В интерфейсе суммируется прогноз прибыли подтверждённых покупок текущей сессии
после комиссии 5%. При каждом запуске сумма сбрасывается, после остановки остаётся
видимой. UNKNOWN, резерв и ручная отметка не считаются успехом. При QTY AMBIGUOUS
прогноз по-прежнему рассчитан по 1 шт.; фактическое количество не подтверждено.

## Режимы

| Режим | Что делает |
|---|---|
| Replay | Один проход по файлу скриншота, без ввода в игру |
| Наблюдение — по умолчанию | Один проход по активному экрану игры, без кликов |
| Проверка меню (без BUY) | Один Search → выбор → перепроверки → открытие/проверка меню; завершение без покупки |
| Автопокупка | Search → выбор в группе → перепроверки → BUY → результат → новый Search |

При первом запуске OCR загружается и прогревается **до захвата экрана**. Модель
сохраняется на одном рабочем потоке между Старт/Replay, циклами и паузами до закрытия
приложения. Повторный запуск использует готовую модель; отдельная строка показывает
время подготовки. Фоновых вычислений во время простоя нет. Это устраняет повторную
ленивую инициализацию, но не гарантирует одинаковое время на любых текстах и нагрузке.

После подготовки экранного режима даются 3 секунды, чтобы активировать игру.
Нужен основной монитор 1920×1080, полноэкранная игра, чистый список аукциона без меню
и уведомлений. По наблюдению пользователя новые лоты обычно появляются сверху вниз,
иногда на второй или третьей строке. Бот выбирает сверху вниз. Поле заголовка окна должно совпадать с реальным окном;
`STALZONE` — начальное значение из описания проекта, не проверенное название процесса.

«Группа лотов» **1 / 3 / 9** задаёт, сколько строк сравнивать:

- **1** — первый подходящий сверху.
- **3** — оценить строки 1–3 и выбрать лучшую подходящую; если кандидатов нет,
  перейти к 4–6, затем 7–9.
- **9** — сравнить все первые девять строк.

«Выбирать по»: прибыль в рублях после комиссии или доходность (прибыль / выкуп × 100%).
Сравнивается прибыль всего лота. При равенстве выигрывает верхний. ROI для выбора
не округляется; в таблице проценты показаны с двумя знаками. «Выбран» отмечает
единственного кандидата, «Подходит» — остальные допустимые лоты группы.
После попытки покупки список обновляется; остаток старой группы не используется.

Технический NAME OCR batch независим от группы; он остаётся в JSON как `batch_size`
и в CLI как `--batch`. По измерениям текущей CPU-схемы batch 1 быстрее и выбран
по умолчанию. Старый JSON сохраняет OCR batch; новые поля `group_size=1` и
`selection_metric="profit"` по умолчанию сохраняют прежний выбор первого подходящего.
QTY/BUYOUT читаются только для предметов, найденных в каталоге.

«Проверка меню (без BUY)» отправляет клики только Search и выбора лота. Нужен
подходящий лот в каталоге и отсутствие неразрешённой покупки. Режим делает один
проход, не создаёт BUY_SENT, не списывает бюджет и оставляет меню открытым.
Кадр и решение сохраняются в `data/diagnostics/probe-<id>/`. Закройте меню вручную
перед следующим запуском. Если кандидата нет или проверка не прошла, BUY также
не отправляется. Это подготовка к проверке ввода, а не подтверждение автопокупки.

### Отдельная проверка кликов без перемещения мыши

Запустите `Test_Background_Clicks.cmd`. Остановите основной бот, откройте аукцион
без меню/уведомлений, наведите курсор на **Search** в активной игре и нажмите **F6**.
Скрипт запомнит точку относительно окна. За следующие **5 секунд** переключитесь
в другое приложение на втором мониторе. Будут отправлены **3 клика** с интервалом
**2 секунды**; **Escape** или Ctrl+C останавливает проверку. F6 только читается,
не блокируется: игра также может обработать эту клавишу. Точку выбирает пользователь;
не выбирайте BUY/OK и не меняйте страницу аукциона во время проверки.

Скрипт `tools/background_click_probe.py` использует PostMessage, не вызывает
перемещение системного курсора или активацию окна. В консоли показан фокус игры
до/после каждого клика. Отправка сообщений не доказывает их обработку игрой:
проверьте визуально Search, свободную мышь и сохранение фокуса другого приложения.
Для сравнения повторите запуск, оставив игру активной. Если клики проходят только
с фокусом на игре, сценарий одновременной работы во втором приложении не подтверждён.
Оставьте игру видимой (при необходимости используйте оконный режим без рамки);
при сворачивании, изменении размера или закрытии окна проверка прекращается.
При ошибке PostMessage повторного нажатия нет. У игры и скрипта должен быть
одинаковый уровень прав. Сам probe не меняет настройки и БД основного бота.
Пользователь подтвердил корректную работу мини-скрипта 2026-10-19;
переключение способа кликов в основном боте описано ниже.

Параметры необязательны, например один клик после 10 секунд:

```powershell
.\.venv-benchmark\Scripts\python.exe -X utf8 tools\background_click_probe.py --count 1 --delay 10
```

`--title` задаёт часть заголовка (по умолчанию STALZONE), `--interval` — интервал
1–60 с, `--hold-ms` — удержание 10–1000 мс (по умолчанию 100).
Проверка не захватывает экран и не подтверждает пригодность фонового OCR/автопокупки.

### Ввод основного бота

На вкладке запуска поле **«Клики»** переключает **«Курсором»** (по умолчанию)
и **«Без курсора»**. Остановите текущий запуск, выберите способ и нажмите «Старт»;
выбор сохраняется в `data/settings.json` (`click_mode`: `cursor` / `background`).
Он применяется к Search, выбору лота, BUY и OK, включая восстановление экрана.

«Без курсора» отправляет WM_MOUSEMOVE / WM_LBUTTONDOWN / WM_LBUTTONUP через
PostMessage, как мини-скрипт, без перемещения мыши и активации игры. Можно работать
на втором мониторе. Окно игры должно покрывать основной экран 1920×1080;
размер 1920×1081 также допускается. Не сворачивайте и не перекрывайте игру,
OCR по-прежнему читает экран 1920×1080 без масштабирования.
При поиске окна точный заголовок имеет приоритет перед совпадением по части названия;
кандидаты должны покрывать основной экран. Проводник с `stalzone.exe` в заголовке
на втором мониторе не мешает выбору игры. При нескольких подходящих окнах бот
сообщает их заголовки и не отправляет ввод.
Бот запоминает выбранное окно и прекращает ввод при его закрытии, сворачивании,
изменении заголовка, положения или размера. Ошибка отправки не повторяет DOWN
и не переключает ввод автоматически на курсор. Полный цикл этого режима в игре
после интеграции ещё не проверен; сначала используйте «Проверка меню (без BUY)».

«Курсором» использует Windows SendInput и требует активного окна игры.
Каждый клик: перенос курсора → ожидание 30–50 мс → проверка фокуса и координат →
нажатие → удержание 30–50 мс → отпускание. Оба интервала выбираются независимо
заново на каждый клик. Эти начальные задержки ещё требуют
проверки в игре; координата Windows не подтверждает готовность игрового курсора.
В JSON доступны `mouse_move_wait_ms` и `mouse_button_hold_ms` (10–1000 мс),
оба по умолчанию 40; `mouse_jitter_ms=10` задаёт отклонение ±10 мс (0–100 мс).
Итоговые границы ограничены 10–1000 мс; jitter=0 отключает случайность.
В режиме «Без курсора» те же настройки и пресеты: ожидание после WM_MOUSEMOVE
и удержание между DOWN/UP. Отдельных задержек из мини-скрипта нет.
Перед повторным OCR в обоих режимах бот ждёт, пока меню остаётся видимым,
а поля NAME/QTY/BUYOUT выбранной строки не меняются минимум 30 мс. Это ожидание
отрисовки внутри таймаута меню 500 мс; пауза между проверками меню — 15 мс.
Задержки самих кликов не изменяются.
Строгие проверки лота и пикселей перед BUY сохраняются. Причина отмены записывается
в `purchase_timing.skip_reason` (внутри `purchase_timings`); для отмен на проверке
меню/OCR/пикселей фонового режима кадры и сравнения сохраняются в
`data/diagnostics/skipped-*`, ссылка — `skip_diagnostic`. Повтора BUY нет.
В UI есть исходный пресет 40+40 мс ±10, ускоренные 20+20 и 10+10 мс без разброса.
Последний — эксперимент: приём кликов игрой проверяйте через «Проверка меню (без BUY)».

После нормального live-цикла и неизменного Search дополнительной паузы нет.
`cycle_interval_ms` оставлен только для чтения старых JSON и не используется.
Search, захваты и OCR выполняются последовательно. Параметры сохраняются при Старт/Replay:

- **По изображению (без OCR)** — исходный кадр используется как образец для
  сравнения полей лотов. Опрос начинается сразу после клика; фиксированная задержка игнорируется.
- **Фиксированная задержка** — после заданного ожидания делается один новый захват
  и проверка чистого аукциона. Смена списка и стабильность не проверяются; при
  короткой задержке возможен анализ старого списка. Время считается после отпускания Search.

По умолчанию выбран первый режим (`search_mode=changed`), статический — `static`.
В обоих режимах перед исходным кадром указатель переносится на Search без нажатия.
Бот ждёт стабильности полей всех девяти строк в течение `search_stable_ms`, чтобы
исчезновение подсветки после OK не считалось обновлением списка. Затем нажимает
Search без повторного перемещения и ожидания мыши. Дополнительного OCR здесь нет.
Пустая таблица ждёт отрисовки до `settle_timeout_ms`; если остаётся пустой и стабильной,
Search всё равно разрешён. Если поля продолжают меняться до таймаута, Search/OCR/BUY
пропускаются (PRESEARCH_UNSTABLE); live повторяет подготовку, проверка меню завершается.
Это уже сравнение с изображением до Search, дополнительный OCR обновления не выполняется.
В changed сравниваются NAME, QTY и BUYOUT, без таймеров и OCR. После изменения
поля всех девяти строк должны оставаться одинаковыми минимум `search_stable_ms=30`
мс и на двух или более наблюдениях. Это защищает polling=0 от принятия двух
захватов одного игрового кадра. Финальный полный кадр сверяется со всеми девятью
строками и проверяется на чистый интерфейс; именно он передаётся OCR.

Если за `settle_timeout_ms=800` после завершения клика изменений нет, live сразу
повторяет Search после проверки интерфейса. Старый список не попадает в OCR или BUY,
критическая ошибка не показывается. Однопроходная проверка меню завершается NO_CHANGE.
Если изменение замечено, но стабильности нет (включая возврат к исходному списку),
бот ждёт ещё один `settle_timeout_ms`. Если список так и не стабилизировался,
сохраняется диагностика UNSTABLE, OCR/BUY пропускаются и live повторяет Search.
Потеря фокуса или неудача восстановления интерфейса останавливают ввод.
Стабильность пикселей остаётся эвристикой, не ответом сервера.

В UI доступны таймаут, окно стабильности и `search_poll_ms`: 0 — без sleep,
5 — быстрый вариант по умолчанию, 30 — экономный. Эти значения не меняют опрос
меню и результата покупки. `search_capture_region=true` захватывает область полей
через Pillow bbox; OCR получает обычный полный кадр с прежними координатами.
По умолчанию `search_monitor_rows=9`. Четыре строки доступны как эксперимент:
при отсутствии изменения сверху контроль к половине таймаута расширяется на девять; перед OCR также проверяются все девять.
Старые явно сохранённые значения таймаута сохраняются; 800 мс — default новых настроек.

Флажок **«Проверка лота OCR после открытия меню»** (`revalidate_lot`, по умолчанию true)
включает одно повторное чтение выбранного лота после открытия меню.
До клика по строке повторного OCR нет. Выключение использует исходные имя/количество/цену и ускоряет этап
после выбора кандидата, но не показатель «До решения». Подмена строки до открытия
меню при этом может остаться незамеченной. Проверка меню по шаблону (без OCR),
сравнение последнего кадра перед BUY, актуальный бюджет, пауза/стоп и защита от
повторного BUY остаются включены. Оба переключателя действуют в probe и live;
наблюдение/Replay не выполняют покупку и Search.

В проверке меню для каждого завершённого анализа, даже без кандидата, сохраняется
`data/diagnostics/search-<id>/`: `before_search.png`, `screen.png` (точный вход OCR),
`detail.json` с временами и признаками захватов. Запись выполняется после анализа.
При UNSTABLE сохраняются исходный и последний полные кадры;
в этом случае `screen.png` не передавался в OCR. Путь успешной диагностики записан
в событии probe (`search_diagnostic`); путь при UNSTABLE указан в событии диагностики.
Обычный UNCHANGED не создаёт PNG и не раздувает журнал SQLite.

Время «анализ» включает NAME, QTY, BUYOUT, сопоставление и выбор. Отдельная строка
показывает стадии, захват (в автопокупке — Search с ожиданием), проверку экрана и
«До решения» — время от начала получения кадра до выбора кандидата. Загрузка моделей,
стартовые 3 секунды, отрисовка UI и последующая покупка не включены. Полные измерения
сохраняются в событиях наблюдения/Replay в SQLite; CLI JSON содержит стадии анализа
и отдельный `preparation` (загрузка/прогрев). Подготовка UI записывается в событие `ocr_preparation`.

Дополнительная строка Search разделяет исходный захват, проверку экрана, клик
(перенос/удержание), фактически прошедшую заданную паузу, новые захваты, сравнения
и паузы между опросами. Отдельно измеряются проверки интерфейса, число сравнений,
число/среднее/максимум новых захватов, время первого изменения и до стабильности,
накопительное число Search без изменений. JSON содержит подробные времена мыши.
Общее время может включать небольшие накладные расходы сверх этих частей.

Для покупки показаны накопительные времена **от начала того же цикла перед Search**:
до успешной отправки DOWN кнопки BUY в Windows, до распознавания результата
на кадре, а также интервал BUY → результат. Это не момент физического появления
окна между захватами и не подтверждение обработки клика игрой. Отдельно показаны
повторный OCR, клик лота, ожидание меню и ожидание ответа после завершения клика BUY.
В проверке меню/при отмене отсутствующие BUY и результат обозначаются «—».
Подробности сохраняются в событиях SQLite `purchase_timing` и диагностике покупки;
UNKNOWN не получает выдуманного времени распознавания результата.

**F8** — пауза/продолжение; **F9** — стоп. Если BUY уже отправлен, контроллер сначала
завершает ожидание результата: по умолчанию 1000 мс, настраивается в JSON.
Пауза между проверками результата — 40 мс.
После продолжения бот проверяет аукцион и пытается закрыть оставшееся меню/уведомление.
На время запуска F8/F9 регистрируются как глобальные горячие клавиши Windows:
короткие нажатия сохраняются в очереди, удержание F8 не переключает паузу повторно.
Если клавиши заняты другой программой, запуск блокируется с сообщением.

Replay принимает 1920×1080 и 1920×1081 без масштабирования. Он не выполняет ввод в игру,
но CLI создаёт/открывает БД; UI также сохраняет настройки, бюджет и событие Replay.
Для проверки используйте отдельную БД:

```powershell
.\.venv-benchmark\Scripts\python.exe main.py --replay "dataset\templates\Обычный скриншот.png" --db "data\replay-test.sqlite3" --group-size 3 --selection-metric profit --batch 1 --output "data\replay-test.json"
```

## Неопределённость и история

Непрочитанный QTY остаётся AMBIGUOUS; для расчёта берётся нижняя оценка 1.
Неизвестная/перекрытая цена пропускается; мусор OCR не удаляется ради получения числа.
Подробнее о выбранных моделях, качестве и ограничениях — [OCR](../docs/OCR.md).

Перед BUY сохраняется BUY_SENT. Незавершённый BUY_SENT блокирует дальнейшие покупки,
включая перезапуск. UNKNOWN запускает проверку и восстановление экрана: до трёх
попыток закрыть распознанное уведомление или убрать меню через Search за 1 секунду.
Интервал повторных кликов — не менее 300 мс после завершения предыдущего клика;
пауза между проверками состояния — 15 мс.
Старое значение общей паузы после уведомления в JSON игнорируется; ожидание возврата
баланса применяется отдельно в режиме «Бюджет из игры».
Изменившаяся строка перед BUY отменяет кандидата и после восстановления возвращает к Search.

При выключенном OCR баланса, если после UNKNOWN аукцион чистый, история получает **UNKNOWN_RECOVERED**, бот продолжает
работу после нового Search и обычных проверок перед BUY. В режиме changed требуется
изменившийся стабильный список. Известное расхождение: static снимает барьер после
задержки без проверки изменения списка (A03 в [аудите](AUDIT_2026-10-20.md)).
Возможная стоимость однократно резервируется в локальном бюджете. Совпадение названия,
цвета, заточки и цены с прежней попыткой не идентифицирует серверный лот и не блокирует
новые покупки, в том числе после перезапуска. Восстановление не повторяет клик BUY.
Это не подтверждение успешной покупки. «Результат проверен вручную» не объявляет успех
и не возвращает резерв автоматически: при необходимости поправьте бюджет.
Неудавшееся восстановление сохраняет UNKNOWN и останавливает сессию; следующий live-запуск
снова проверит экран. История содержит решение, результат и путь к диагностике.

Шаблоны SUCCESS, UNAVAILABLE и INSUFFICIENT проверены на предоставленных изображениях.
«Недостаточно денег для совершения ставки» распознаётся как **Недостаточно средств**:
бюджет не списывается, бот останавливается, окно остаётся открытым, повторный BUY
блокируется до ручного разбора истории. После пополнения проверьте игру и снимите
блокировку кнопкой «Результат проверен вручную». Новый шаблон проверен офлайн;
полноэкранная проверка в игре ещё нужна. Другие неизвестные окна остаются UNKNOWN.
Стабильность пикселей после Search — эвристика, не подтверждение ответа сервера.
