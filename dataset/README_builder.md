# Dataset Builder для StalBot

Инструмент ручной разметки. Использует Python 3.10+, Tkinter (из стандартной
установки Python) и Pillow. Не запускает main.py, не управляет игрой, не выполняет OCR.

## Запуск

На данном компьютере: двойной щелчок по `run_builder.cmd`. Скрипт использует только
`..\.venv\Scripts\python.exe` из проекта; глобальный Python и runtime Codex
не подставляются. Pillow установлен в это окружение. Предыдущий вывод о поломке
`.venv` был ошибочным: проверка в sandbox не могла запустить установленный Python,
но вне sandbox Python 3.12.0 и Tkinter работают. Устаревший путь в поле `command`
файла pyvenv.cfg — история создания, а не рабочий путь интерпретатора.

Для независимой установки откройте PowerShell в папке dataset после установки
Python с компонентом Tcl/Tk:

```powershell
py -3 -m venv ..\.venv
..\.venv\Scripts\python.exe -m pip install -r requirements-builder.txt
..\.venv\Scripts\python.exe builder.py
```

Другой датасет: `python builder.py --dataset "C:\path\to\dataset"`.

## Работа

1. Поместите оригинальные PNG/JPEG/BMP в `screenshots/pending`.
2. Проверьте рамки на изображении аукциона. Если открыто меню покупки, выберите
   номер лота, после которого оно появилось (0 — меню закрыто). Подтвердите рамки
   флажком. Смена геометрии требует повторной проверки всех строк.
3. Введите видимое имя полностью, включая `| +15` и точки сокращения. Выберите цвет
   имени; семантическую редкость артефакта/экипировки программа не угадывает.
4. Выберите состояния заточки, количества и выкупа. Пустые поля не означают 0 или 1.
5. Нажмите «Разметить →» или Ctrl+Enter. Выбор строки слева и Alt+Left/Alt+Right
   позволяют вернуться к ней. Изменённая строка требует повторного подтверждения.
6. Нечитаемое наложение BID/BUYOUT или пустую строку пропустите с причиной.
   Скриншот с уведомлением, прокруткой или неподходящими рамками отложите целиком.
7. После проверки всех строк сохраните весь скриншот. Только тогда он покинет pending.

Черновик автоматически записывается после паузы во вводе (400 мс), при переходах
и закрытии окна. В текстовых полях работает Ctrl+V на русской и английской
раскладках Windows, а также правая кнопка мыши → «Вставить». Выделенный текст
заменяется содержимым буфера обмена.

Черновик сохраняется при переходах
и закрытии окна. Потеря питания в течение этих 400 мс может потерять последний ввод,
но не исходник. Черновики лежат в `labels/drafts`, не являются готовой разметкой.
«Отложить» сохраняет черновик и оставляет файл в pending; «Обновить очередь» возвращает
отложенные файлы в работу. Новые файлы появляются в очереди после её обновления.

Состояния:

| Поле | Состояние | Сохранённое значение |
|---|---|---|
| QTY | VALUE | Введённое положительное целое |
| QTY | ABSENT | 1, только после ручного подтверждения отсутствия цифр |
| QTY | AMBIGUOUS | null |
| BUYOUT | VALUE | Введённое положительное целое без лимита покупки |
| BUYOUT | ABSENT | null, на скриншоте `---` |
| BUYOUT | AMBIGUOUS | null |
| Заточка | VALUE | Видимый суффикс, значение 0..15 |
| Заточка | NOT_VISIBLE | null, суффикс не отображается |
| Заточка | UNKNOWN | null, не удалось установить |

`NOT_VISIBLE` намеренно не превращается в 0: по одному сокращённому имени нельзя
доказать, что суффикс отсутствует, а для части предметов заточка неприменима.
Известный артефакт без суффикса можно интерпретировать как +0 позднее по правилам
каталога. Это отделяет наблюдаемый текст от игрового значения.
Цвета хранятся как `white/green/blue/purple/red/gold/unknown`; UNKNOWN не получает
выдуманного названия редкости. Имя с `..`/`…` получает `name_truncated=true`.
Пропущенные строки сохраняют номер и причину, но не попадают в размеченные кропы.

## Измеренная геометрия

Координаты `(left, top, right, bottom)`, правая и нижняя границы не включены.
Ось X направлена вправо, Y вниз. Область таблицы аукциона без фильтров:
`(882, 370, 1387, 766)`; строки занимают Y=393..763.

| Область первой строки | Координаты | Размер |
|---|---|---|
| Полный лот | (887, 393, 1386, 430) | 499×37 |
| NAME | (927, 394, 1140, 413) | 213×19 |
| QTY | (889, 409, 926, 430) | 37×21 |
| BUYOUT | (1230, 399, 1384, 424) | 154×25 |

Для строки с индексом i=0..9 прибавляется 37*i к обеим Y-координатам.
При открытом меню после лота k=1..9 к строкам i>=k добавляются ещё 37 пикселей;
видимыми остаются 9 лотов. Меню и страницы не становятся лотами.

Все 38 предоставленных файлов имеют размер **1920×1081**, вопреки 1920×1080 в README.
Поддерживаются оба размера без ресайза. Координаты измерены на 1081; на новом
источнике 1080 обязательно проверить совпадение рамок. Иные размеры отклоняются.

Игровые снимки 1081 и будущие снимки экрана 1080 не нужно приводить к единому
размеру. Кропы используют абсолютные координаты и заканчиваются на Y=763,
поэтому последняя строка Y=1080 в них не участвует. Ресайз 1081→1080, напротив,
изменил бы пиксели текста. Дополнительный тест подтверждает идентичность всех
ROI при удалении только нижней строки. Это моделирование, а не доказательство
одинакового положения UI при двух способах захвата: настоящего парного снимка
аукциона 1920×1080 пока нет. Пустой/дублированной последнюю строку считать нельзя:
в исследованной выборке она содержит изображение и отличается от предыдущей.
Оригиналы сохраняются как есть. Документация координат и crop:
https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.crop

BUYOUT содержит все разряды видимой цены 9 999 999 999, валюту и запас.
При длинном BID левый край BUYOUT может содержать его окончание; при экстремальных
ценах BID также заходит в NAME. Эти пиксели не удаляются и не дорисовываются.
При невозможности однозначно отделить цену пропускайте лот. Увеличение ROI не
восстановит перекрытые символы или сокращённый игрой конец имени.

## Сохранение и восстановление

`labels/labels.json` содержит `schema_version=1` и словарь `screenshots`, ключ —
SHA-256 исходного файла. Для каждого скриншота сохраняются исходное имя, размер,
путь к оригиналу, версия геометрии, положение меню и строки. У каждой размеченной
строки есть значения, состояния, координаты и четыре пути/контрольные суммы кропов.
Обработанный исходник переименовывается в `<sha256>.<расширение>`; оригинальное имя
сохраняется в JSON. Это предотвращает коллизии одинаковых имён.

1. Проверяются все строки и неизменность исходника.
2. Записываются PNG-кропы без масштабирования, фильтров и рамок. Готовый файл
   публикуется атомарно и никогда не перезаписывает отличающийся существующий кроп.
3. После проверки кропов атомарно заменяется labels.json (временный файл + fsync + replace).
4. После повторной проверки контрольных сумм исходник переносится в processed:
   создаётся жёсткая ссылка, затем удаляется имя из pending. Байты не изменяются.

Несколько файлов нельзя атомарно заменить одной обычной файловой операцией.
Поэтому атомарность здесь логическая: labels.json — точка фиксации готовой записи,
а перенос оригинала восстанавливаемый. После сбоя до фиксации могут остаться
неиспользуемые кропы; повторная обработка проверяет их и использует заново.
После сбоя между фиксацией и переносом следующий запуск завершает перенос без
дублирования разметки. Зафиксированная запись уже завершена: новые правки черновика
при повторе переноса не применяются. При повреждённом кропе исходник остаётся в pending.
Не удаляйте кропы и не редактируйте labels.json вручную во время работы.

Запуск второго Builder для того же датасета блокируется ОС. Неизвестный существующий
формат labels.json не перезаписывается. Хранилище рассчитано на локальный диск с
поддержкой жёстких ссылок (например NTFS), с pending/processed на одном томе.
Сетевые/облачные синхронизируемые папки и аппаратная потеря данных не проверялись;
транзакционное сохранение не заменяет резервное копирование.

## Проверки

```powershell
python -m unittest -v test_builder
python check_geometry.py --dataset . --output ..\geometry-review
```

При разработке прошли 20 тестов: валидация, геометрия, сохранение, сбои кропов/JSON/
переноса, конфликты, повреждение кропов, смена исходника, дубликаты, блокировка,
а также настоящий Tkinter: ввод, переходы, пропуск, черновик, следующий скриншот.
GUI-тест вызывает обработчики программно; длительная ручная сессия мышью не проведена.

Визуально изучены все 12 hard_cases и 6 templates, выборка обычных скриншотов;
просмотрены NAME/QTY/BUYOUT всех 120 строк hard_cases. На всех 32 рабочих скриншотах
проверены 1280 кропов: пиксели совпадают с соответствующими областями исходника,
SHA-256 исходников не изменились. Это не проверка качества будущего OCR.

Файлы: `builder.py` — UI; `builder_core.py` — геометрия, валидация и хранилище;
`test_builder.py` — тесты; `check_geometry.py` — воспроизводимая проверка кропов;
`requirements-builder.txt`, `run_builder.cmd`, этот документ — установка и запуск.
