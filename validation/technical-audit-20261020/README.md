# Технический аудит StalBot — 20 октября 2026

Основной вывод: быстрее всего бот станет за счёт захвата, проверок интерфейса и
обработки после результата. Массовое отключение защит даст меньший выигрыш и
уберёт проверки, которые действительно отклоняли устаревшие кандидаты.
Повторный OCR — не главная задержка. Его можно условно заменить точным сравнением
исходных пикселей, но нынешний переключатель `revalidate_lot=false` этого не делает.

Рабочий код, настройки, модели, каталог и база не изменены. Весь новый материал
находится в этом каталоге. Ввод в игру не выполнялся. Проверки покупки используют
fake desktop и временные БД. Это аудит и план изменений, а не внедрение ускорений.

## Основания и границы выводов

- Прочитаны основной цикл, Scanner, экономика/каталог, SQLite, распознавание UI,
  OCR, кеш и его сохранение, адаптеры Windows, hotkeys, запуск и потоки UI.
- SQLite прочитана через URI `mode=ro`, `query_only=ON`, в одной read-транзакции:
  11 369 событий, 6298 `purchase_timing` (6293 live), 4526 попыток, 205 правил.
  `PRAGMA quick_check`: `ok`.
- Разобраны 5386 `detail.json`, журнал исключений и релевантные предыдущие
  исследования. Не загружались целиком модели/датасет ради поиска файлов.
- Основная таблица ниже: **151 отправка BUY в режиме cursor за 20 октября по
  Asia/Chita**, время записи 01:36:31–07:50:44, event id 10889–11359.
  Для всех найден соответствующий diagnostic/attempt; у всех есть `balance_before`.
  Последняя предшествующая запись подготовки указывает DML, но полного снимка
  конфигурации и session id в каждом событии нет: это ограничение атрибуции.
- В этой же серии было 191 вхождение в purchase, из них 40 без отправки BUY.
  Из 151 отправленной попытки уведомление распознано у 149: SUCCESS 115,
  UNAVAILABLE 34; ещё 2 — UNKNOWN. Это наблюдённые статусы, не ручная проверка покупок.
- Последние игровые purchase-логи предшествуют изменению `runner.py` в 08:20:22.
  **Ни одно событие не содержит `prepare_ms`.** Новая подготовка Search уже есть
  в коде и unit-тестах, но её игровой latency этими логами не измерен.
- В live циклы без кандидата и обычные UNCHANGED не сохраняются в SQLite.
  Поэтому числа описывают выбранную выборку попыток, а не все Search, не частоту
  сканирования за час и не вероятность покупки случайного нового лота.
- Проект не является Git checkout в этом каталоге. Для воспроизводимости
  сохранены SHA-256 и mtime исходников в `metrics.json`.

Расчёты: [analyze.py](analyze.py), [metrics.json](metrics.json),
[индекс событий](timing-index.json). Квантили — линейная интерполяция по позиции
`(n−1)q`. При отсутствии метрики значение не заменяется нулём.
Сопоставление diagnostic с событием — по точной тройке времён BUY/result и только
при единственном совпадении; не по приблизительному соседству timestamps.

**Почему нельзя просто убрать OCR-перепроверку.** В последней cursor-серии
34/191 (17,8%) вхождений в purchase завершились «Выбранный лот изменился»;
ещё 4 — меню не стабилизировалось, 2 — строка изменилась перед BUY.
В background за тот же местный день: 541 вхождение, 370 BUY, 152 отклонения
из-за смены лота, 16 по меню и 3 по финальному кадру. Это не доказывает, что
каждое отклонение было истинной подменой (возможен OCR/рендеринг), но доказывает,
что ветки работают часто и требуют разбирательства перед удалением.
Сравнение cursor/background не является контролируемым A/B-тестом.

Fake-воспроизведение: исходное решение по цене 80, новая стабильная строка по
90 до меню. `revalidate_lot=true` даёт STALE, без BUY; `false` отправляет BUY
по старому решению. Последний pixel guard сравнивает кадры **после** открытия
меню и такой переход не замечает. Это известный риск существующей опции,
а не обнаруженная поломка обычного включённого режима.

## Найденные технические проблемы

1. **P1 — static обходит свежесть после UNKNOWN.**
   `Runner.fresh()` сбрасывает `needs_fresh_search` для любого ненулевого кадра
   ([runner.py](../../stalbot/runner.py), строки 207–215), включая STATIC_DELAY.
   Fake-воспроизведение возвращает неизменившийся кадр и сбрасывает барьер.
   После UNKNOWN_RECOVERED это разрешает следующую попытку без требуемого
   изменившегося стабильного списка. Это не повтор DOWN внутри одной попытки,
   а обход барьера между попытками. Текущая настройка changed не задействует дефект.
   Исправление: требование fresh после UNKNOWN должно принудительно использовать
   changed и сниматься только по CHANGED_STABLE; учесть восстановление/перезапуск.

2. **P2 — PNG задерживает надёжную фиксацию результата и следующий цикл.**
   `_purchase` сначала вызывает `diagnostic()`, затем `finish_buy()` (507–509).
   При зависшем диске уже распознанный исход долго остаётся BUY_SENT; при аварии
   остаётся консервативная блокировка, а не автоматический повтор покупки.
   Исправление: сначала зафиксировать исход/бюджет, потом передать неизменяемый
   кадр и JSON в ограниченную очередь. Сбой диагностики не должен портить статус.
   Путь/состояние сохранения диагностики обновлять отдельно; BUY_SENT не асинхронизировать.

3. **P2 — стоп проходит через загруженный Tk-поток.**
   Поток Hotkeys кладёт событие в очередь; `App.poll()` ставит stop/pause только
   при следующем опросе, назначенном через 100 мс. Там же полностью перестраивается
   история (`refresh_history`, строка 569) и обрабатывается вся очередь без лимита.
   Пока UI занят, worker видит старый cancel. Нажатия не теряются, но немедленной
   остановки нет. Предлагается доставлять F9 прямо в thread-safe Event, отделить
   переключение F8 от отрисовки и ограничить работу UI за тик. После отправленного
   BUY всё равно завершать наблюдение. Величина задержки UI в игре не измерена.

4. **P2 — недостаточно телеметрии для полного latency-профиля.**
   Нет постоянных session/cycle id, снимка настроек/версии кода в каждом запуске,
   компактной статистики циклов без кандидата, разбивки commit/PNG/recovery/balance.
   `purchase_timing` не содержит attempt id и наблюдённый исход; сейчас их пришлось
   восстанавливать через JSON-файлы. PNG/detail снимаются до `purchase_total_ms`.
   `errors.log` не содержит временных меток. Новые prepare-метрики не показаны в UI
   отдельными полями. Вводить агрегаты/ограниченный trace, а не писать PNG каждого Search.

5. **P2 — полная история и диагностика растут без ограничения.**
   13 834 файла в `data/diagnostics`, 4 239 201 326 байт (~3,95 GiB).
   Очистка UI скрывает записи и сохраняет аудит, но не освобождает это место.
   Нужна явная политика хранения успешных кадров с сохранением спорных случаев;
   удаление не выполнялось. SQL unresolved сейчас даёт `SCAN attempts`;
   добавить соответствующий индекс при подтверждённом выигрыше. Все 4526 строк
   сами по себе не авария, но повторные полные обходы растут вместе с историей.

6. **Остаточные ограничения визуальной идентификации.**
   Изменение RGB — не серверный lot id; старая таблица/поздний ответ всё ещё могут
   быть приняты за изменение после стабилизации. Перед кликом строки кадр есть,
   но с исходным решением его пиксели не сравниваются. Между последним проверенным
   кадром, commit и DOWN сохраняется окно гонки. Его надо сокращать, а не называть
   устранённым. Уникальный префикс в каталоге также не гарантирует уникальность
   предмета во всей игре: повторный OCR того же сокращения не решает эту проблему.
   Для дорогих/коллидирующих сокращений нужен дополнительный признак предмета
   или полный текст, а не ещё один одинаковый OCR-вызов.

7. **Документация местами отстала.**
   DEVELOPMENT_PLAN в начале ещё упоминает блокировку совпадающего лота, хотя
   ниже описывает её отмену. ARCHITECTURE одновременно описывает разрешённые
   уникальные сокращения и содержит фразу «Сокращённые имена ... отклоняются».
   requirements-bot говорит только о CPU, хотя runtime поддерживает DML.
   Отчёт старого Search-исследования описывает код до сегодняшней правки:
   его результаты не следует читать как описание нынешнего `_fresh`.

## Измеренные компоненты и порядок ускорения

Свежие офлайн-замеры: [probes.py](probes.py), [probes.json](probes.json).
Один статический чистый кадр, cv2 threads=2, по 25 повторов UI/SQLite.
Это измерения отдельных компонентов без контроля игровой нагрузки.

| Компонент | p50, мс | Вывод |
|---|---:|---|
| Проверка auction | 0,44 | Дешёвая |
| Девять позиций меню | 1,19 | Не главный расход |
| blocking_modal | 5,03 | Дороже сравнений полей |
| Три шаблона outcome | 14,99 | Главный расход чистого UI |
| clean_auction | 24,27 | Много раз вызывается в полном цикле |
| Снимок полей всех 9 строк | 0,059 | Нет смысла начинать с оптимизации array_equal |
| PNG default level 6 | 79,19 | CPU-время сжатия одного реального полного кадра, без диска |
| PNG level 1 | 46,64 | На том же кадре ~32,5 мс быстрее; размер 625 708 → 956 120 байт |
| Чтение balance через новое SQLite-соединение | 1,82 | Небольшие, но повторяющиеся расходы |
| begin_buy + finish_buy во временной короткой БД | 23,88 | Две надёжные транзакции вместе, не стоимость одного intent |
| Одно event во временной БД | 11,60 | Не помещать подробную телеметрию синхронно в каждый polling |

PNG level 1 проверен на побитовое совпадение декодированных RGB. Это полезный
резервный вариант, но очередь диагностики лучше устраняет задержку основного цикла.
Не суммировать медианы независимых микроизмерений в прогноз полного цикла.

Приоритет внедрения:

1. **Исправить static/UNKNOWN и добавить полную разбивку стадий.** Ускорения
   сравнивать с текущей подготовкой Search, а не только с предыдущими логами.
   Основные метрики: cycle→DOWN, возраст принятого кадра при DOWN, outcome→next Search,
   доли STALE/UNKNOWN/ошибок восстановления и FPS/frametime игры.
2. **Ускорить захват.** В сохранённом [исследовании 16 октября](../../benchmarks/OPTIMIZATION_20261016.md)
   Pillow region9 p50 21,98 мс против 5,74 у native GDI с повторным буфером.
   Это прошлый desktop-бенчмарк, не обещание такого же выигрыша в игре.
   Внедрять с текущими проверками окна/DPI/отмены и независимыми RGB-копиями.
   Выигрыш нескольких снимков может быть существеннее 19 мс повторного OCR.
   Нельзя умножить разницу на все 8 захватов: часть работы перекрывает ожидание игры.
3. **Ускорить классификацию UI и подготовку Search.** Один результат классификации
   на один кадр, повторное использование score/позиции OK при recovery; меньшие
   проверенные ROI. Не считать наличие/отсутствие OK полноценной заменой outcome
   без тестов всех известных и неизвестных диалогов. Подготовку сравнивать регионами,
   сохранив финальное подтверждение чистого полного кадра.
4. **Вывести PNG из критического пути после результата.** На измеренном кадре
   только сжатие занимает ~79 мс; отложенная запись также уменьшает задержку
   закрытия уведомления. Очередь ограниченная; outcome/бюджет остаются синхронными.
5. **Сделать сверку баланса событийной.** Для UNAVAILABLE раньше выходить при
   подтверждённом возврате ожидаемой суммы; 700 мс оставить fallback/минимальным
   консервативным ожиданием там, где исход UNKNOWN и временное списание неотличимо
   от успеха. Потенциально это самый большой выигрыш до следующего цикла, до части
   фиксированных 700 мс, но не ускорение текущего BUY. Нужны live-трассы возврата.
6. **Условно пропускать повторный OCR по точному равенству исходных полей.**
   Ожидаемый потолок выигрыша на совпавшем кадре соответствует нынешним ~19–30 мс.
   Передать исходные поля решения, сравнивать NAME/QTY/BUYOUT полностью; при любом
   отличии сохранять OCR. Не кешировать решение, текущий бюджет или неизвестный QTY.
   Hover может снизить долю совпадений; измерить её до внедрения нормализации.
7. **Числа и каталог — следующий уровень.** Внутри Scanner сейчас BUYOUT ~44 мс,
   NAME ~0,18. Можно исследовать изолированные native numeric workers и предварительный
   индекс нормализованных правил; окупаемость зависит от числа совпавших строк и
   конкуренции CPU с игрой. Не делить один Tesseract API между потоками. BUYOUT-first
   может экономить QTY на отказах по общей цене, но медиана QTY всего ~1,2 мс.

Что не даст ожидаемого выигрыша:

- `search_wait_ms=20` в changed уже не используется; `wait_ms=0` в выборке.
- `cycle_interval_ms=300` не задаёт паузу нормальных live-циклов: её уже убрали.
- Polling 0 не превращает захват 33 мс в мгновенный. Суммарный sleep 83 мс нельзя
  целиком вычесть из цикла: при частом polling может появиться больше захватов.
- `group_size=1/3` вместо 9 меняет стратегию выбора. GPU всё равно получает
  эффективный NAME batch9, но можно раньше прекратить числовое чтение. Это обмен
  качества ранжирования на задержку, не эквивалентная оптимизация.
- Увеличивать кеш NAME сейчас не главный приоритет: последний завершённый запуск
  дал 2067 hits / 6 misses (99,71%), 5000 entries и 6 evictions, ~60,7 MB RGB.
  Этот hit rate относится к одному запуску, не ко всем логам. Нынешний CPU/GPU
  выбор мало влияет на медиану при попадании в кеш, но влияет на хвост промахов.
- Снижение 1000/500/800 мс таймаутов не вычитает эти числа из успешного пути:
  это пределы ожидания результата/меню/Search, а не обязательные sleep.
- Меньшие задержки мыши могут помочь, но пресет 20+20 в реальной серии давал
  около 58 мс на клик. Срок сна и принятие ввода игрой надо измерять, а не
  предполагать равными настройке. Переход на background не доказан ускорением.

  В тестах fake WinAPI/desktop и временные БД; Tk smoke не равен ручной работе UI.

  выключенный reread допускает заменённую стабильную строку, включённый отклоняет.
  Эти скрипты подтверждают находки, а не исправляют их. [Результаты](probes.json).
- **Полная DML-регрессия OCR: PASS**, код завершения 0 и `Integration regression passed`.
  NAME 170/170 для batch 1/3/9; прежний baseline покрытия не изменён.
  Проверены кеш/Scanner, групповые стратегии, числовой OCR и UI-шаблоны.
  [Лог](integration-dml.log), [JSON](integration-dml.json).

  68 QTY, 81 BUYOUT; нет независимого доказательства отсутствия ошибок на новых

- 1420 исторических balance_check: 1078 SUCCESS→SUCCESS, 293
  UNAVAILABLE→UNAVAILABLE, 47 UNKNOWN→UNAVAILABLE, 1 UNKNOWN→SUCCESS,

  причину роста: это может быть внешнее изменение счёта/разрыв между попыткой
