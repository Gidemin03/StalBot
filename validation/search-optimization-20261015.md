## Логика Search

1. Полный кадр и проверка чистого аукциона перед Search; проверка фокуса остаётся в Desktop.
2. После завершения клика changed сразу опрашивает поля. `search_wait_ms` применяется только в static.
3. Точно сравниваются RGB-поля NAME/QTY/BUYOUT. Таймеры и промежутки исключены.
   По умолчанию девять строк; четыре — экспериментальный триггер, после изменения расширяемый на девять.
4. Нужно отличие от исходного списка и минимум два наблюдения неизменных полей всех девяти строк
   на протяжении `search_stable_ms=30` мс. Каждое новое изменение сбрасывает окно.
   Затем берётся полный кадр, проверяется интерфейс и совпадение всех девяти строк с последним наблюдением.
   Если поля поменялись, стабилизация продолжается. OCR получает именно проверенный полный кадр.
5. За `settle_timeout_ms=800` изменений нет: финальный полный кадр должен быть чистым и совпадать
   с исходными полями всех девяти строк. Fresh возвращает UNCHANGED/None; live сразу повторяет Search,
   без OCR, BUY, PNG и критической ошибки. Счётчик накапливается. Одноразовый probe завершается NO_CHANGE.
6. Изменения замечены, но стабильности нет, либо кадр вернулся к исходному: UNSTABLE,
   диагностические полные кадры и остановка ввода. Если четыре строки пропустили изменение снизу,
   финальная проверка девяти строк запрещает повторный Search поверх этого состояния.
7. После нормального live-анализа нет cycle_interval_ms. Старое поле JSON сохранено для совместимости.
   Ошибки интерфейса, фокуса, незакрытого меню/диалога останавливают ввод; Pause/Stop прерывают ожидание.

При polling=0 не вызывается искусственный sleep. 30-мс окно стабильности сохраняется,
иначе два быстрых захвата одного отображённого кадра могли бы ошибочно считаться окончанием перехода.
Это дополнительное наблюдение, а не фиксированная пауза перед началом опроса.

У стандартного диалога проверяется общий контур кнопки OK: неизвестный текст не позволяет дальнейший ввод,
даже если заголовок аукциона остаётся виден. Этот guard также проверяется при меню и перед BUY.
Он никогда не присваивает статус покупки; SUCCESS/UNAVAILABLE/INSUFFICIENT/UNKNOWN работают как прежде.

определения конкретных строк нет. Это причина сохранять проверку всех девяти строк.

## Варианты мониторинга

Одинаковые 16 сохранённых кадров, включая шесть before/after пар и четыре dataset-скриншота.
На каждой итерации — подготовка текущих полей и два сравнения. Значения в миллисекундах.

| Вариант | p50 / p95 | Пикселей | Массивов с копиями RGB |
|---|---:|---:|---:|
| A: NAME+QTY+BUYOUT ×9, прежние crop+concat | 0,128 / 0,259 | 78 066 | 28 |
| B: NAME+BUYOUT ×4 | 0,037 / 0,074 | 31 588 | 9 |
| C: NAME+QTY+BUYOUT ×4 | 0,045 / 0,093 | 34 696 | 13 |
| D: точные срезы ×4, без копирования RGB | 0,129 / 0,242 | 34 696 | 0 |
| Срезы ×9 | 0,292 / 0,542 | 78 066 | 0 |
| Компактная упаковка ×9 | 0,115 / 0,234 | 78 066 | 1 |
| Итоговый FieldMonitor ×9, включая валидацию | 0,125 / 0,265 | 78 066 | 1 |
| Итоговый FieldMonitor ×4 | 0,049 / 0,107 | 34 696 | 1 |

Подготовка через concatenate(axis=None) копирует каждое выбранное RGB-поле в один итоговый буфер,
без отдельных crop().copy(). Срезы/объекты Python и временные bool-массивы сравнения в последнюю
колонку не входят. Итоговый монитор примерно равен baseline по скорости; значительного выигрыша
этой операции нет. Меньше ROI/копий не означает автоматически меньше времени.

На шести реальных парах все варианты согласны: четыре различаются, две одинаковы.
На синтетике все находят изменения NAME/BUYOUT во второй–четвёртой строках; B пропускает
изменение только QTY. Все четырёхстрочные варианты пропускают изменение только пятой/девятой строки.
Все игнорируют выбранный прямоугольник таймера. Полноценные частоты ложных/пропущенных обновлений
не установлены: нет размеченной временной последовательности серверных ответов.

## Polling и мышь: только модели

Это детерминированная модель на измеренной стоимости захвата и 30-мс окне стабильности.
Она исключает начальную проверку, финальный полный кадр, клик и OCR; это не время всего Search.

| Polling, мс | До готовности p50 / p95, мс | Задержка обнаружения p50 / p95, мс | Среднее кадров | Среднее sleep, мс |
|---:|---:|---:|---:|---:|
| 0 | 210,89 / 289,98 | 12,72 / 25,08 | 7,80 | 0 |
| 5 | 183,17 / 277,25 | 15,17 / 29,81 | 6,12 | 25,59 |
| 30 | 251,81 / 308,17 | 27,81 / 53,08 | 4,51 | 105,45 |

В этой модели 5 мс даёт готовность раньше 0 из-за попадания следующего захвата за границу
30-мс окна стабильности. 0 быстрее обнаруживает первое изменение. Нельзя объявлять один
polling самым быстрым в игре по этой модели. Process CPU time сохранён в JSON; влияние
на FPS игры и p95 OCR под нагрузкой не измерено.

| Настройка мыши | Сумма заданных ожиданий p50 / p95, мс |
|---|---:|
| 40+40 ±10 | 79,90 / 93,63 |
| 20+20, jitter0 | 40 / 40 |
| 10+10, jitter0 | 20 / 20 |

Это не измерения доставки кликов игрой и не фактические интервалы SendInput. Последовательность
SetCursorPos → проверка фокуса/позиции → DOWN → удержание → UP сохранена; UP в finally,
повторного DOWN при ошибке нет. 10+10 уменьшает заданные задержки в четыре раза,
но приём такого клика Stalzone ещё требуется проверить. Значение по умолчанию 40+40 ±10 сохранено.

| Метрика | Прежняя версия | Новая версия |
|---|---|---|
| Игровой Search | 561 мс в указанном примере | Не измерен в игре |
| Игровое время до решения | 713 мс по сообщению пользователя | Не измерено в игре |
| Фиксированная задержка в changed | Выполнялась | Отсутствует, проверено fake clock |
| Пауза между live-циклами | cycle_interval_ms, default300 | Отсутствует, проверено тестами |
| Обычный неизменный таймаут | Остановка запуска | Повтор Search, без OCR/BUY |
| Проверки UI в каждом опросе | Да | На границах ожидания |
| Кадр OCR | Полный | Полный, проверены все девять строк |

Из этих строк нельзя вычислить фактический новый игровой Search простым вычитанием:
число опросов, серверная задержка и поэтапное обновление меняют последовательность.

Диагностика содержит полный Search, клик, исходный/новые захваты, их количество/среднее/максимум,
стоимость пиксельных сравнений и их количество, отдельные UI-проверки, фактические sleep,
первое изменение, готовность и счётчик UNCHANGED. OCR и выбор кандидата остаются в cycle_timings;
клик строки, ожидание меню, ready_ms в probe и время DOWN BUY в live — в purchase_timings.
Накопительные времена нельзя складывать с их компонентами. В probe запись PNG Search перед
проверкой меню входит в общее время до ready_ms, но не в Search и decision_ms; сравнивайте это отдельно.

## Конфигурация и игровая проверка без BUY

Начальный быстрый профиль: changed, timeout800, polling5, stable30, monitor9,
region=true, повторный OCR=true. Старые явно сохранённые параметры не перезаписываются;
если timeout был1800, вручную поставьте800 в UI.

Для поиска максимальной скорости сравните polling0 и5 на одном живом интерфейсе;
30 оставьте контрольным экономным вариантом. Четыре строки пока не рекомендуются:
захват почти не ускоряется, а полнота обнаружения ниже. Из быстрых кликов сначала
проверьте20+20/jitter0;10+10/jitter0 используйте только после подтверждения приёма игрой.

1. Выберите «Проверка меню (без BUY)», сохраните исходный пресет40+40 ±10.
2. На подходящих лотах повторите не менее20 наблюдений для каждого polling0/5/30
   с одинаковыми остальными настройками; чередуйте варианты и сохраняйте probe/search диагностику.
   Отдельно учитывайте UNCHANGED и UNSTABLE; не смешивайте их с готовыми обновлениями.
3. Аналогично сравните40+40,20+20,10+10. Успешный SendInput не считается приёмом клика:
   нужны наблюдаемое обновление и открытое меню; после каждого probe закройте меню вручную.
4. Сравните Search/decision/ready p50/p95, число кадров, CPU, FPS/frametime игры и p95 OCR.
   Зафиксируйте промахи Search/меню, частоту нестабильных переходов и фоновую нагрузку.
   При неизвестном окне или потере фокуса ввод должен прекратиться. Покупки для этой проверки не нужны.

Пиксельное отличие не является подтверждением ответа сервера; одинаковый ответ безопасно пропускается.
30-мс окно и полный финальный кадр не исключают произвольно позднюю смену нижних строк.
Generic modal guard распознаёт известный стиль окна с OK, не любые будущие окна игры.
Это явные ограничения визуального протокола, а не доказанная готовность реальной автопокупки.
