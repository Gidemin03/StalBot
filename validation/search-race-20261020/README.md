## Причины в текущем коде

1. `Desktop.capture/capture_region` каждый раз вызывает ImageGrab; повторное использование
   сохранённого кадра не обнаружено. Scanner получает кадр, возвращённый fresh().
2. `_fresh()` снимает baseline до переноса указателя на Search. FieldMonitor сравнивает
   точные RGB всего NAME/QTY/BUYOUT, включая фон. Снятие hover достаточно для changed.
   Если оно стабильно, полный контроль девяти строк подтверждает тот же ложный сигнал.
3. `clean_auction()` проверяет оболочку/меню/уведомления, но не готовность содержимого.
   Поэтому восстановление допускает пустую таблицу. Её заполнение старым списком также
   может быть принято за обновление. Это дополнительный воспроизведённый сценарий,
   а не доказанный источник ложного сигнала именно данного Search.
4. Перед выбором строки `_purchase()` снимает новый кадр, но не сопоставляет его лот
   с исходным кадром сканирования. Сверка содержимого происходит после открытия меню.

Наиболее вероятный триггер в данном эпизоде — снятие подсветки шестой строки.
Исходный before_search и принятый OCR-кадр этого успешного live Search не сохранены,
поэтому точный пиксельный триггер по видео с компрессией окончательно не доказать.

## Воспроизведение

`reproduce.py` использует настоящие Runner/FieldMonitor и существующий fake desktop/clock.
Для двух сценариев (снятие подсветки; пустая таблица → старый список) текущий fresh()
вернул старый список как CHANGED_STABLE через 24 мс при обновлении данных на 300 мс.
Результат — reproduction.json. 24 мс относятся только к синтетическому времени,
а не измерению скорости игры. Никаких реальных вводов или покупок не было.

## Предлагаемое исправление

1. Перед baseline убрать реальный/виртуальный указатель из строк на Search без нажатия,
   дождаться завершения изменения подсветки и готового содержимого. Затем снять baseline
   и нажать Search без дополнительного переноса. Не принимать пустую/недорисованную таблицу
   за базу свежести после покупки. При ожидании/таймауте не запускать OCR кандидатов и BUY.
   Учесть нормальные пустые результаты поиска: они не должны приводить к вечному ожиданию.
2. Подтверждать обновление по содержимому полей с учётом состояний загрузки и фоновой
   подсветки. Любую нормализацию сравнения отдельно проверить на изменениях одной цифры,
   количества, цвета и заточки. Не ослаблять строгость OCR и финальных проверок BUY.
3. Перед открытием меню сравнить выбранную строку нового кадра с кадром, по которому
   принято решение. При несовпадении отбросить кандидата. Это уменьшит лишние клики;
   обновление между проверкой и кликом всё ещё возможно, поэтому double validation сохранить.
4. При STALE сохранять соответствующую трассу Search: baseline, принятый кадр,
   кадр перед выбором, изменения по полям и время. Это позволит различить hover,
   промежуточную отрисовку и задержанный ответ, а также проверить исправление.

После SUCCESS/UNAVAILABLE нужен контроль обновления списка, но не вечный запрет
одинаковых предметов/цен: разные лоты могут иметь одинаковые параметры.
Восстановление через Search тоже отправляет запрос: при реализации учитывать уже
запущенное обновление, чтобы не путать его с новым Search следующего цикла.

Просто увеличить settle_timeout_ms недостаточно: ошибочный ранний выход случается
до таймаута. Увеличение search_stable_ms — лишь временная мера; search_wait_ms в changed
вообще не используется. Из видео нельзя вывести гарантированную задержку сервера.

Проверка будущей правки: fake hover в cursor/background, пустой промежуточный кадр,
задержанные и поэтапные ответы, одинаковые лоты после свежего ответа, изменение между
scan и кликом, отмена/таймаут, однократный BUY; затем проверка меню без BUY в игре.
