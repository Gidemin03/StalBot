# Выбор OCR для StalBot — 14 октября 2026

Это первый этап. Актуальные выводы после проверки новых гипотез: [REPORT2.md](REPORT2.md).

Реализован и выполнен локальный benchmark: **12 070 ответов OCR**, три семейства
движков, CPU/DirectML, шесть вариантов подготовки изображения. Варианты для следующей
проверки зафиксированы в [candidates.json](candidates.json).

## Что выбрать сейчас

| Поле | Кандидат | Результат | CPU p50 / p95 на кроп |
|---|---|---|---|
| NAME | RapidOCR, кириллическая PP-OCRv5, `content3` | 157/170 (92,4%); 139/140 обычных, 18/30 сложных | 34,8 / 66,1 мс |
| BUYOUT | Tesseract rus+eng, PSM 7, `otsu3` | 146/153 видимых цен; 158/170 с учётом состояний | 20,0 / 51,7 мс |
| Видимые цифры QTY | RapidOCR, английская PP-OCRv5, `scale3` | 54/54; на 116 ABSENT — 23 ложных значения больше 1 | 27,3 / 31,5 мс |
| Альтернатива QTY | Tesseract, PSM 8, цифры, `white3` | 53/54; ошибка 64→454; чисел на 116 ABSENT не выдал | 9,8 / 15,6 мс |

**Для QTY полного решения пока нет.** Пустой ответ OCR не доказывает отсутствие
цифры: он может означать ошибку чтения. Поэтому программа возвращает AMBIGUOUS,
а не подставляет 1. RapidOCR предпочтителен для чтения уже обнаруженной цифры;
Tesseract с маской белого текста — более быстрый кандидат с меньшим числом ложных
ответов в этом наборе. Выбирать между ними для всего QTY без отдельной проверки
наличия текста преждевременно. Детектор присутствия количества этим benchmark
не реализован.

Tesseract `otsu3` для NAME — более быстрая альтернатива: 155/170 при 26,8 мс p50.
Преимущество RapidOCR всего два примера, оно ещё не подтверждено независимой выборкой.
Оба кандидата правильно прочитали видимую заточку в 13/14 случаев.

У лучшего BUYOUT все 146 принятых числовых значений верны на текущих данных.
Правильно распознаны 5/10 ABSENT; все 7 AMBIGUOUS отклонены. Остальные 12 ошибок —
семь отказов на видимой цене и пять нераспознанных ABSENT. Это не доказательство
нулевого риска ошибки на новых скриншотах. На сложных примерах правильны лишь
19/30 состояний/значений BUYOUT, на обычных — 139/140.

## Нужна ли подготовка изображения

Да, но разная для каждого поля. Для NAME удаление пустого фона по ярким пикселям
с полем 2 px, затем увеличение ×3 дало RapidOCR 157/170 против 149/170 без внешней
подготовки. Оно сохраняет все яркие компоненты, включая попавшие в NAME цифры BID.
Эта помеха остаётся существенной причиной ошибок сложных примеров.

Для BUYOUT увеличение ×3 и Otsu улучшили Tesseract с 149 до 158 правильных случаев.
Обычное увеличение также дало 158, но приняло одно неверное числовое значение;
вариант Otsu не принял неверных чисел на этой выборке. Уменьшение BUYOUT слева
на 10 px дало Tesseract 153/170: **оснований менять сохранённый кроп сейчас нет**.
Исходные кропы Builder не изменялись; все преобразования выполнялись в памяти.

Для QTY общая бинаризация Otsu ухудшила RapidOCR с 54/54 видимых значений после
увеличения до 35/54. Маска светлых малонасыщенных пикселей особенно помогла
Tesseract: 53/54 вместо 44/54 на исходном кропе. Устанавливать один preprocessing
для всех полей по этим результатам не стоит.

EasyOCR в проверенных конфигурациях уступил: лучший NAME — 137/170 при 242 мс p50;
для QTY ограничение алфавита цифрами часто превращало фон в уверенные ложные числа.
Контроль без ограничения алфавита не сделал его победителем. Это вывод о конкретной
модели `cyrillic_g2` и этих настройках, а не о всех возможных вариантах EasyOCR.
Ранняя кириллическая модель RapidOCR также заметно уступила PP-OCRv5.

## CPU, GPU и пакетная обработка

Компьютер: Ryzen 5 3600 (6 ядер / 12 потоков), GTX 1660 6 ГБ, Windows, Python 3.12.
GPU измерен через ONNX Runtime DirectML. Профилировщик подтвердил 298 событий узлов
на DirectML и 2 на CPU — проверено реальное выполнение, а не только список
доступных провайдеров. [Подтверждение](profile2/gpu_proof.json).

Повторный профиль RapidOCR v5: исходные кропы, 18 лотов из двух скриншотов,
прогрев и три измеряемых повтора, два CPU-потока. Это отдельный эксперимент;
цифры ниже нельзя переносить на выбранный `content3` без измерения.

| Поле | CPU, batch=1 | DirectML, batch=1 | CPU, batch=9 | DirectML, batch=9 |
|---|---:|---:|---:|---:|
| NAME | 45,4 мс | 17,1 мс | 579,1 мс | 131,2 мс |
| QTY | 29,0 мс | 14,5 мс | 319,3 мс | 106,1 мс |
| BUYOUT | 29,7 мс | 79,7 мс | 322,2 мс | 105,5 мс |

В таблице медиана **всего пакета**. Например, GPU BUYOUT batch=9 — около 11,7 мс
на изображение по пропускной способности, но первый результат надо ждать около
105,5 мс. Нельзя объявлять это задержкой первого решения в 11,7 мс.
При изменении batch size 1/3/9 ответы в профильной выборке не изменились.

Шесть CPU-потоков вместо двух почти не помогли одиночным кропам: NAME 47,6 против
45,4 мс, QTY 28,9 против 29,0 мс, BUYOUT 29,1 против 29,7 мс. Один поток был медленнее.
Для следующего этапа оставлены два потока. Порядок прогонов фиксирован;
это не статистически рандомизированное сравнение производительности.

**GPU не обязателен для текущего кандидата**, но ускоряет некоторые варианты
RapidOCR. Включать его сразу для всех полей невыгодно: одиночный BUYOUT через
DirectML здесь медленнее CPU, а лучший движок цены — Tesseract. CUDA EasyOCR и
нагрузка одновременно с работающей игрой не измерялись. Требование по задержке
полного рабочего цикла ещё не проверено.

## Данные, исправления и пределы выводов

17 скриншотов, 170 размеченных лотов: 140 обычных и 30 из трёх сложных скриншотов.
Уникальных точных кропов NAME/QTY/BUYOUT — 75/68/81. Для выбранных NAME и BUYOUT
точность по уникальным кропам — 84,0% и 86,4%. Повторы существенно завышают впечатление
от общей точности. Разнообразие количества ограничено значениями 2, 5, 10, 18, 34,
48, 50, 64 и 100; больших количеств в размеченной выборке нет.

После визуальной проверки исправлены четыре подписи, с резервными копиями:

| Скриншот / лот | Было | Стало |
|---|---|---|
| 2026-10-14_10.15.05.png / 2 | Ключ от заводского сейв | Ключ от заводского сейфа |
| 2026-10-14_10.20.41.png / 8 | 2669999 | 2699999 |
| 2026-10-14_10.37.01.png / 4 | 4300000 | 430000 |
| 2026-10-14_13.18.16.png / 9 | Экзоброная «Гектор» | Экзоброня «Гектор» |

Сохранены исходные ответы OCR; после исправлений они пересчитаны по новым
эталонам, без повторного inference. Парсер цен также ужесточён: разрешены только
целая числовая строка с корректными группами тысяч и допустимый суффикс валюты.
Произвольные буквы не удаляются, соседние BID и BUYOUT не склеиваются.
Старые manifest и резервные копии доступны для проверки. Ответ `1100000`, который
сначала вызвал подозрение при просмотре контактного листа, уже был правильным
в JSON и не менялся.

Варианты выбраны на тех же данных, по которым рассчитана точность. Это исследование
и выбор кандидатов, **не независимый тест и не готовый модуль автопокупки**.
Цвет/редкость, соответствие каталогу и торговые правила здесь не оцениваются.
Высокая confidence не гарантирует правильный ответ. Следующий этап — проверка
зафиксированных вариантов на оставшихся новых скриншотах и отдельный детектор QTY
VALUE/ABSENT. Переразмечать оставшиеся hard cases для воспроизведения этого запуска
не требуется.
