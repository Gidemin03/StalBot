# OCR: выбранная схема и границы проверки

Основной корень проекта — `C:\Users\demid\Documents\PythonProj\StalBot`.
Рабочая реализация находится в [vision.py](../stalbot/vision.py), правила разбора
и наблюдений — в [domain.py](../stalbot/domain.py). Производственный код не импортирует
benchmark-скрипты. Исследовательский выбор и причины отказа от альтернатив описаны
в [REPORT2.md](../benchmarks/REPORT2.md); первый [REPORT.md](../benchmarks/REPORT.md)
сохранён как история, а не текущая рекомендация.

## Поля и обработка

| Поле | Текущая схема |
|---|---|
| NAME | Очистка компонентов ниже строки имени, обрезка по яркому содержимому с запасом 2 px, увеличение ×3 bicubic → RapidOCR Cyrillic PP-OCRv5 mobile, CPU или одна DirectML-сессия |
| Заточка | Разбор `| +N` из NAME; отдельного OCR нет. Допустимый видимый суффикс +1…+15; повреждённый ответ не обрезается до +15 |
| QTY | Геометрическая проверка светлых малонасыщенных компонентов → маска белых цифр, ×3 → Tesseract rus+eng, PSM 8, whitelist цифр |
| BUYOUT | Увеличение ×3 + Otsu → Tesseract rus+eng, PSM 7, строгий разбор всей числовой строки |
| Баланс (опция) | ROI (1000,804)–(1388,826), ×3 + Otsu → тот же native Tesseract, PSM 7 без whitelist; полная строка «Счет: N руб.» |
| Цвет | HSV по буквам верхней строки после очистки NAME |

RapidOCR работает без детекции текста и классификатора поворота.
Баланс читает `stalbot/balance.py` вне кеша NAME: нужны метка, целое число и валюта;
отсутствие/обрезка текста, знаки, дроби и повреждённые группы цифр дают AMBIGUOUS.
Ноль допустим; цифры из мусора не извлекаются. Runner подтверждает значение на
двух отдельных чистых кадрах и отдельно ждёт возможного возврата после отказа.
[Проверка 36 кадров](../validation/balance-ocr-20261019/README.md) дала 36 совпадений,
но содержит только 3 различных баланса; реальные нулевые/очень большие значения
и задержки обновления живого счёта ещё не проверены.
Дополнительный OCR цены и отдельные модели заточки не включены в рабочий Reader.
Для CPU используются два потока; Reader принадлежит создавшему его потоку.
UI сохраняет его в `OcrSession` между запусками до закрытия приложения.
`Reader.warmup(batch_size)` до получения игрового кадра прогоняет искусственные
NAME/QTY/BUYOUT-кропы в памяти через те же пути распознавания. Числа прогреваются
один раз, каждый технический размер NAME-пакета — один раз. Эти ответы не являются
наблюдениями лотов. Прогрев не изменяет разметку, веса или правила распознавания;
он переносит отложенную инициализацию в отдельную фазу подготовки.
Локальные веса: `benchmarks/models/rapid/cyrillic_PP-OCRv5_rec_mobile.onnx`,
`benchmarks/models/tessdata/rus.traineddata` и `eng.traineddata` в той же папке tessdata.
Технический `batch_size` 1/3/9 относится к NAME на CPU; начальное значение — 1.
При `ocr_device=dml` эффективный batch равен 9; сохранённый CPU batch не меняется.
Группа выбора `group_size` 1/3/9 в UI — отдельный параметр стратегии сравнения лотов.
На историческом интеграционном
прогоне batch 9 был медленнее batch 1, поэтому большой пакет не считается ускорением.

Известная геометрия требует RGB 1920×1080. Replay также принимает 1920×1081
без масштабирования. FreshLots читает первые девять строк с шагом 37 px;
координаты и происхождение кропов описаны в [документации Builder](../dataset/README_builder.md).

## Точный кеш NAME

UI и CLI Replay используют [CachedNameReader](../stalbot/name_cache.py) поверх
штатного Reader на выбранном устройстве. Значение `name_cache_capacity` по умолчанию 1000;
допустимо 0..100000, 0 полностью обходит кеш. Ключ — форма исходного uint8 RGB-кропа
и все его байты; хеш таблицы не заменяет полное сравнение. Даже один изменённый
пиксель создаёт другой ключ. В кеше только неизменяемая Identity: название, цвет,
заточка и признаки распознавания, включая отказы. QTY, BUYOUT, каталог, бюджет,
история и решения не кешируются; проверки свежести и повторного BUY сохранены.

Кеш в памяти принадлежит одному Reader и его потоку. Совместимый снимок загружается
с диска при создании; CPU/GPU имеют раздельные файлы. Прогрев делегируется исходному Reader, поэтому полностью
выполняет native OCR и не создаёт cache entries/hits. Изменение ёмкости между запусками
не перезагружает модель; уменьшение вытесняет самые давние записи, 0 очищает память,
но не перезаписывает прежний дисковый файл пустым кешем.

UI показывает hits/misses/evictions за текущий запуск, включая повторный NAME в меню;
размер кеша учитывает и записи прошлых запусков. Статистика вычисляется за O(1).
Итог пишется событием `name_cache` в существующий журнал БД, в CLI — полем JSON.
`pixel_bytes` учитывает только сохранённые RGB-байты, а не весь RSS процесса.
Оценка 12 МиБ для 1000 записей основана на прототипе; оптимальная ёмкость
для разных игровых сессий ещё не определена. В одном пакете одинаковые промахи могут быть
распознаны несколько раз: счётчики отражают запросы кропов, а не уникальные ключи.
Внедрение проверено полной регрессией; результаты и ограничения — в
[отчёте](../validation/name-cache-20261016.md).
В [десятиминутном тесте пользователя](../validation/cache-live-user-20261016/README.md)
1416 попаданий, 246 промахов, 246 записей и 0 вытеснений: для этой серии лимита хватает.

## Сохранение NAME-кеша

[cache_storage.py](../stalbot/cache_storage.py) хранит только форму/RGB и Identity
в порядке LRU от давних к свежим. Файлы UI: `data/name-cache/cpu.names`, `dml.names`;
CLI позволяет отдельный `--name-cache-dir`. У файла версия формата, fingerprint,
строгая схема записей и SHA-256 всего содержимого. Не используется pickle.
Проверяется весь файл до принятия любой записи, включая записи сверх текущей ёмкости.
При ошибке размера/схемы/контрольной суммы/совместимости загрузка целиком отклоняется.
Лимиты разбора: 100000 записей, 2 ГиБ файла, 32 КиБ JSON на запись, 4 МиБ RGB на запись.
После загрузки остаются последние записи в пределах `name_cache_capacity`.

Fingerprint включает байты ONNX со встроенным словарём, дополнительные словари/
конфиги, исходники обработки/разбора/кеша и RapidOCR, версии OCR/runtime/numpy/OpenCV
и формат. CPU/GPU разделены и в имени файла, и в metadata. Для обоих устройств
задан явный `Rec.model_path`: ленивый загрузчик не подменяет fingerprinted файл
автоматической загрузкой весов. Ошибка fingerprint отключает дисковое сохранение,
не мешая обычному OCR. Консервативная проверка может очистить кеш после обновления кода.

Владелец ридера передаёт writer неизменяемый снимок ссылок на bytes/Identity.
Один фоновый поток пишет временный файл в том же каталоге, делает fsync и atomic replace.
Кроме текущей записи хранится не более одного ожидающего снимка; более свежий
заменяет ожидающий. Запись не обращается к native OCR или изменяемому OrderedDict.
Проверка автосохранения выполняется после NAME, на границах циклов и во время паузы;
изменения, включая перестановку LRU при попаданиях, сохраняются не чаще раза в 60 с.
Время может сдвинуться до ближайшей безопасной точки выполнения. Остановка и закрытие
принудительно сохраняют dirty-кеш и ждут writer; при ошибке завершения есть одна
повторная попытка. Ошибки видны в persistence-метриках и UI, OCR не останавливается.
При аварийном завершении процесса последние несохранённые изменения могут потеряться.

Capacity 0 не загружает/не записывает файл; повторное включение загружает прежний снимок.
Уменьшение ёмкости сохраняет только удержанные свежие записи. Статистика попаданий
не сохраняется: она относится к текущему запуску. Несколько процессов имеют отдельную
память и атомарно заменяют файл; их кеши не объединяются, побеждает последняя запись.

## CPU / GPU

`Reader(models, device='cpu'|'dml')` использует те же веса и preprocessing.
CPU-путь остаётся прежним. GPU устанавливает одну ONNX Runtime DML-сессию с
`ORT_SEQUENTIAL`, `enable_mem_pattern=False`, intra/inter threads 2/1.
Проверяется первый провайдер `DmlExecutionProvider`; скрытый runtime fallback
на другую сессию отключён. CPU provider остаётся для отдельных неподдерживаемых
операций, поэтому режим GPU не означает полное отсутствие вычислений на CPU.
QTY/BUYOUT, геометрия и цвет всегда обрабатываются прежним CPU-путём.

`OcrSession.get_reader(..., key=ocr_device, reader_factory=...)` при смене ключа
сначала сохраняет кеш и закрывает старый Reader, затем создаёт новый, загружает
совместимый кеш выбранного устройства и прогревает модель.
Одновременных GPU-ридеров и совместного кеша CPU/GPU нет. Ошибка загрузки/прогрева
останавливает подготовку; следующий явный выбор CPU позволяет продолжить работу.
Прогрев идёт до захвата экрана и отправки игрового ввода.
`backend_info()` записывает фактические providers/options в подготовку UI и CLI JSON.
Общее время подготовки при переключении включает освобождение предыдущего ридера.
Ускорение полного цикла и FPS под игровой нагрузкой офлайн-проверки не подтверждают.
Полная DML-регрессия, CPU → GPU → CPU и профиль исполнения проверены:
[отчёт внедрения](../validation/gpu-switch-20261016.md).

## Семантика отказов

- QTY без принятого числа остаётся `AMBIGUOUS`, включая отклонение геометрическим
  фильтром. Это не доказательство `ABSENT` и не исправление эталона.
- Для расчёта `conservative_quantity=1` при `AMBIGUOUS`/`ABSENT` — нижняя оценка
  при наличии хотя бы одного предмета, верно определённых предмете и полной цене лота.
- BUYOUT принимает положительное целое с корректными группами тысяч и допустимым
  суффиксом валюты; строка из тире означает `ABSENT`. Мусор и фрагменты BID
  не удаляются ради получения числа. Неизвестная или отсутствующая цена пропускается.
- Видимый разделитель заточки с непрочитанным числом не превращается в +0.
  Для сокращённого имени +0 устанавливается по прямому игровому правилу пользователя.
  Сокращённое имя сохраняет признак сокращения и допускается к покупке при
  единственном совпадении префикса названия и правила цвета/заточки в каталоге.
  Уникальность префикса в закупочном каталоге не доказывает полный предмет.
- Fuzzy matching и исправление OCR через каталог не используются.
