# Оптимизация StalBot: серия 2026-10-16

Исследование рабочего Reader, без изменения `stalbot/`, настроек пользователя,
рабочей SQLite, моделей, разметки и baseline. Реальный ввод и покупки не запускались.
Основной сценарий — девять строк NAME; технический пакет и группа выбора различаются.

## Данные и протокол

- Исходный [полный OCR baseline](../validation/optimization-baseline-20261016.json)
  прошёл: NAME 170/170, одинаковые Identity в batch 1/3/9, прежние числовые пороги.
- Набор: 170 размеченных строк, 75 уникальных исходных RGB NAME-кропов;
  labels SHA-256 `20de6ed3e416fe9bea5e5ff614e7f9dc194978a4e79b5199108f9ffac94465d1`.
  Это прежний набор выбора вариантов, не независимая оценка точности.
- Windows, Python 3.12.0, RapidOCR 3.10.0, ONNX Runtime DirectML 1.24.4,
  Pillow 12.3.0, Ryzen 5 3600 / GTX 1660. Версии, входы и хеши сохранены в manifest.
- Матрица устройств: 3 раунда, 3 исходных кадра, 8 повторов; 72 замера на каждую
  конфигурацию и объём 1/3/6/9 строк. Шесть строк — отдельная диагностика 3+3,
  **не** новая группа выбора. Порядок конфигураций/входов меняется между раундами.
- Один отдельный процесс на конфигурацию/раунд; тяжёлые benchmark последовательны.
  Native Reader/API создаётся, используется и закрывается на потоке-владельце.
  Профилирование узлов выполняется отдельно от timed samples.
- Нагрузка игры и FPS не контролировались. Существующий пользовательский `main.py`
  не останавливался; во время точечных проверок серии кеша он практически простаивал.
  Эти измерения не доказывают скорость или стабильность под игровой нагрузкой.

Хеши модели, словаря и формы входа, фактические CPU threads 1/2, inter-op=1,
а для DML sequential/memory-pattern=false подтверждены
[инспектором настроек](results/optimization-devices-isolated-20261016-a/effective-settings.json).

## NAME: одинаковые девять строк

Время включает рабочую подготовку RGB, inference, разбор Identity и dispatch.
Чтение файлов, создание моделей и прогрев вынесены за измеряемый интервал.

| Текущий CPU, batch9 | 448,62 | 574,84 |
| CPU 1 worker × 1 внутренний поток | 327,19 | 420,74 |
| CPU 1 worker × 2 потока | 268,88 | 318,41 |

Источник: [сводка](results/optimization-devices-isolated-20261016-a/summary.json),
[все измерения](results/optimization-devices-isolated-20261016-a/measurements.jsonl).
Каждая из 15 устойчивых конфигураций совпала с CPU baseline по всем полям Identity
на 170 кропах; совпадение проверялось и на каждом timed вызове. Завершены 45/45
устойчивых запусков. Числа по-прежнему читает Tesseract CPU.

DML batch9 сокращает p50 NAME относительно CPU batch9 примерно на 74%, p95 — на 75%.
Относительно простого CPU batch1 выигрыш p50 около 40%. Это ускорение NAME на этих
входах; оно не означает ускорения полного игрового цикла в четыре раза.
Для одной строки DML p50/p95 13,36/58,15 мс, CPU batch1 21,44/35,92 мс:
выигрыш медианы сопровождается худшим хвостом. Поэтому выбор зависит от объёма.

CPU pool 2×2 и 3×1 близки; 2×2 проще по числу сессий, но решать между ними надо
по FPS/frametime игры. Гибрид CPU+GPU на девяти строках уступает одному DML batch9;
фиксированное равное распределение также проигрывает динамической очереди.
В варианте фиксированных пакетов шесть строк действительно распределяются 3+3;
для девяти третий пакет снова идёт CPU, то есть распределение 6+3.

В профиле одной DML batch9-сессии за формы 1/3/6/9 зарегистрированы 1192 DML и 8 CPU
событий. GPU действительно исполняет модель, но утверждать отсутствие CPU fallback
нельзя. Одновременные host-вызовы не являются доказательством перекрытия GPU-ядер.
Создание и прогрев учитываются отдельно; сравнивать нужно их сумму, поскольку
production лениво загружает NAME-модель при прогреве, а кандидат — при создании.
RSS — всего процесса, VRAM — снимок всего GPU, не точная стоимость одной сессии.
Например, в первом раунде CPU pool 2×2 имел RSS 134,8 МиБ после прогрева
(до создания кандидата 103,3 МиБ), а DML batch9 — 328,6 МиБ (до 104,1 МиБ).
При дальнейшей обработке RSS DML доходил до 357,4 МиБ. GPU memory.used в тех же
снимках был 1595–1783 МиБ для всего GPU вместе с другими приложениями.
Это ресурсная цена, которую нужно учитывать вместе с выигрышем времени.

### Native-сбой нескольких GPU-сессий

Две и три независимые DML-сессии при параллельном inference вызвали Windows access
violation внутри `onnxruntime.InferenceSession.run`. Каждая сессия принадлежала
своему потоку; конкурентного вызова одной сессии не было. Повтор в отдельном процессе
подтвердил проблему, стек и коды выхода сохранены в
[logs](results/optimization-devices-isolated-20261016-a/logs).
**Эти реализации отвергнуты для внедрения на данной сборке.** Причина на уровне
ORT/драйвера не установлена; результат не обобщается на все версии или все GPU.

`stable_configurations_pass=true`, но `all_candidates_pass=false`: сбои не скрыты.
Предварительная общая серия `optimization-devices-20261016-a` оборвалась и не
используется в таблице; минимальный `optimization-devices-20261016-dml2-probe` также
сохранён. Основные результаты относятся только к завершённой изолированной серии.

Числовой эксперимент использовал весь набор как совпавший с каталогом; реальная доля
совпадений неизвестна. BUYOUT-first не имеет права отказывать по цене за штуку без
QTY. Пропущенный QTY должен оставаться неизмеренным, а не AMBIGUOUS/подтверждённой 1;
порядок диагностических причин (`stack_limit` и др.) требует отдельного решения.

Диагностический writer проверен на ошибки записи и ограниченную очередь с drain.
В рабочем коде PNG после покупки сейчас предшествует `finish_buy`; при будущем переносе
нельзя отправить надёжную фиксацию исхода/бюджета в необязательную очередь.
Сохранение Search-кадров в probe входит в интервал готовности; это не тот же путь, что live.

## Кеш, конвейер и окончательный отбор

### Точный NAME LRU и повторное использование подготовки

[Кеш и подготовка](results/optimization-cache-20261016-a/report.json): проверены
все 170 NAME в batch1/3/9, 96 CPU и 96 GPU corpus-проходов, 768 вызовов штатного
Scanner на двух кадрах с группами 1/3/9, обоими критериями и техническим batch9.
Все Identity и решения совпали с baseline. Каталог временный, числовой OCR свежий.
Кеш хранит исходные RGB+размер+namespace и неизменяемый Identity; точное равенство
пикселей защищает от hash collision. Бюджет, цены, QTY и решение BUY не кешируются.

Медиана **полного прохода 170 NAME**, два повтора, технический batch9:

| Вариант | Холодный кеш, мс | Повтор тех же входов, мс |
|---|---:|---:|
| CPU без кеша | 9273,85 | 10326,76 |
| CPU + LRU18 | 4081,32 | 3896,73 |
| CPU + LRU37 | 4145,27 | 4001,69 |
| CPU + LRU75 | 3943,11 | 3,61 |
| CPU + общая подготовка + LRU75 | 3912,03 | 2,86 |
| DML batch9 без кеша | 2257,80 | 2164,33 |
| DML batch9 + LRU75 | 1390,24 | 2,77 |
| DML batch9 + общая подготовка + LRU75 | 1327,95 | 2,72 |

Здесь «холодный» относится к кешу, модели прогреты. Пакеты corpus могут пересекать
границы исходных кадров; это throughput, не latency девяти строк одного кадра.
В исходном порядке много повторов: даже холодный LRU получает попадания. Повтор
того же набора при ёмкости75 даёт 100% попаданий, но это **не игровой hit rate**.
Два повтора достаточны для отсева крупных эффектов, не для устойчивой оценки p95.
GPU-фазы общей/обычной подготовки шли последовательно; их разницу нельзя полностью
отделить от дрейфа нагрузки. На CPU общая подготовка не дала устойчивого выигрыша
полного corpus: cold 9418,61 против 9273,85 мс без неё.

Изолированная подготовка 170 NAME сократилась с 308,71 до 158,55 мс при побитовом
совпадении подготовленных изображений, цвета и разделителя. Это экономия около
0,88 мс на crop в данной серии, не измеренное сокращение полного цикла.
LRU18/37/75 удерживал примерно 227/466/944 тыс. байт Python-объектов и пикселей;
создание ключа с поиском — около 0,01 мс. Overflow длиннее ёмкости, вытеснение,
почти одинаковые входы, namespace, принудительная коллизия и общие обращения из
потоков проверены. Tracemalloc включает также синтетический входной поток;
отдельная оценка retained bytes описывает именно записи кеша.

[Синтетические последовательности](results/optimization-streams-20261016-a/report.json),
по 30 кадров × 9 строк: сдвиг на одну строку дал 232 hit/38 miss при всех ёмкостях;
повтор кадра — 261/9; изменение одного пикселя каждого входа — 0/270. При замене
всех 9 с циклом по 75 картинкам LRU18/37 дал 0/270, LRU75 — 195/75. Это проверка
политики без OCR. **75 — измеренная точка, покрывающая старый corpus, а не выбранная
ёмкость для игры.** Настройку ёмкости нужно опирать на реальные последовательности.

### Конвейер NAME и чисел

[768 сравнений](results/optimization-pipeline-20261016-a/report.json) прошли без
расхождений: CPU pool 2×2 и DML batch9, группы 1/3/9, request1/9, четыре каталога
(none/all/early/late), оба критерия, два кадра, два повтора. Конвейер предчитает
только следующий нужный пакет текущей группы; отмена ждёт его завершения и
отбрасывает результат. Проверены ошибка worker, повторное использование и закрытие.

При group9 и совпавшем каталоге request1 на CPU ускорился с 422,84 до 288,57 мс
на обычном кадре и с 317,03 до 234,71 мс на сложном. Но простой pool с request9
уже давал 311,55 и 227,17 мс. При основном request9 сам конвейер дал 306,82/230,59
мс — устойчивого выигрыша нет. DML request9 изменился с 287,58/263,94 до
300,62/283,01 мс (обычный/сложный), то есть стал медленнее. Это медианы четырёх
замеров на случай; отдельную надёжную оценку хвоста из них делать нельзя.
Для group1/3 конвейер ещё уменьшает предчтение за границей группы; эту разницу
нельзя приписывать перекрытию вычислений. **Для основного batch9 конвейер отложен.**

### Вердикт по каждому кандидату

«Внедрить» ниже — рекомендация следующего отдельного изменения, не изменение
текущего бота. Перед включением GPU/захвата нужны измерения вместе с игрой.

| Кандидат | Вердикт | Основание |
|---|---|---|
| Точный ограниченный NAME LRU | **Внедрить опционально** | Большой выигрыш при повторах, решения совпали; ёмкость и реальный hit rate ещё подобрать. |
| NAME на GPU, одна сессия batch9 | **Внедрить как опцию после игровой серии** | Лучший NAME p50/p95 на 9 строках; больше RAM, FPS и игровая конкуренция неизвестны. CPU оставить доступным. |
| CPU pool | **Отложить как альтернативу GPU** | 2×2/3×1 полезны, но уступают DML на9; выбор при занятом GPU требует игрового сравнения. |
| Разные строки CPU+GPU | **Отвергнуть для текущего batch9** | Динамическая очередь быстрее фиксированной, но хуже одной DML batch9-сессии. |
| 2–3 сессии одного GPU | **Отвергнуть текущую реализацию** | Воспроизводимый native access violation. |
| Общая подготовка NAME | **Отложить отдельное внедрение; сохранить кандидат в комбинации** | Подготовка дешевле и идентична, но самостоятельный выигрыш полного Scanner/corpus нестабилен. |
| Проверки интерфейса | **Отложить локальный reuse; отвергнуть сужение как самостоятельный выигрыш** | Основной повтор после Search уже устранён; узкий ROI с fallback не быстрее на смешанном наборе. |
| Native GDI region | **Отложить до игровой проверки** | Большой выигрыш capture-call, но возраст/пропуски кадров, фокус и DPI в игре ещё не проверены. |
| Условный повтор OCR выбранного лота | **Отложить** | Точное сравнение дёшево; нужны реальные pre/post-menu пары и влияние подсветки. |
| Polling/клики | **Отложить выбор настроек** | Только модель времени; нет новой серии приёма ввода, UNSTABLE и FPS. |
| QTY+BUYOUT одновременно | **Отвергнуть на текущих данных** | Малый выигрыш медианы, ухудшение p95, дополнительный API. |
| Конвейер NAME+числа | **Отложить для batch9** | Помогает мелким запросам; простой большой запрос сопоставим или быстрее. |
| BUYOUT до QTY | **Отложить** | Небольшая доля дорогого QTY, неизвестна частота абсолютного отказа; меняется диагностика. |
| Диагностика в bounded queue | **Отложить до отдельного изменения цикла** | Сокращает первую отправку, но не полную запись; нужны backpressure и надёжный finish_buy вне очереди. |
| SQLite/UNKNOWN snapshot | **Отложить до значимой истории** | Большой выигрыш повторных lookup при 10 тыс. записей, дорогая сборка; финальная транзакционная проверка остаётся. |

Рекомендуемый порядок: точный кеш с учётом hit/miss → опциональный одиночный DML
batch9 и сравнение с CPU при игре → native capture после проверки свежести.
Не менять одновременно ввод, OCR и guards: следующий шаг должен оставаться
проверяемым отдельно. Реальные покупки автоматически не тестировать.
