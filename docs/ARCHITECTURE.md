Запуск и назначение режимов описаны в [README](../README.md), проверки — в

## Модули и ответственность

| Файл | Назначение |
|---|---|
| `main.py` | CLI Replay или запуск Tk UI; сборка зависимостей и путей |
| `stalbot/config.py` | Проверка настроек, загрузка и сохранение JSON |
| `stalbot/domain.py` | Наблюдения OCR, правила каталога, сопоставление имён/вариантов и экономика |

| `stalbot/vision.py` | Геометрия ROI, preprocessing, OCR NAME/QTY/BUYOUT и цвет |
| `stalbot/ocr_session.py` | Постоянный поток-владелец Reader, подготовка и асинхронное освобождение |

| `stalbot/interface.py` | Шаблоны аукциона, меню BUY и уведомлений |
| `stalbot/runner.py` | Наблюдение и цикл автопокупки, перепроверки, запись результата |
| `stalbot/search.py` | Точные поля Search, региональные координаты и компактное сравнение |

Runtime не импортирует код из `benchmarks/`. Веса OCR размещены в
`benchmarks/models`; UI-шаблоны — в `assets/ui`. Исследовательские результаты
и построение датасета остаются отдельными задачами.

## Поток данных и выполнение

`изображение → Interface → Scanner → Reader → Catalog/evaluate → Decision`.

Полное имя сопоставляется точно. Сокращённое имя без конечных точек сопоставляется
как префикс ровно одного названия среди включённых правил каталога; затем требуется
ровно одно подходящее правило цвета и заточки. Для сокращённого имени заточка +0.
`Rule.upgrade` задаёт точное значение, а при заданном `upgrade_max` — нижнюю границу
включительного диапазона. `upgrade=None` по-прежнему означает «любая». Неизвестный
уровень не попадает в числовой диапазон; пересечения дают `ambiguous_variant`.
Фактическая Identity остаётся точной: перепроверка лота перед BUY не допускает
смену уровня даже внутри одного диапазона.
Уникальность в закупочном каталоге не доказывает уникальность предмета во всей игре.
В автопокупке `Runner` дополнительно управляет `Desktop` и журналом `Store`.

Scanner проходит первые девять строк группами `group_size=1/3/9` и полностью
оценивает каждую группу до выбора. В первой группе с `eligible` выбирается максимум
по `selection_metric=profit/roi`; при точном равенстве — верхняя строка. ROI сравнивается
точной дробью, а не округлённым значением для таблицы. Значение group_size=1 сохраняет
прежний первый подходящий. Проверки бюджета, лимита и прибыли предшествуют ранжированию.
NAME читается пакетами 1/3/9 на CPU или 9 на GPU (`Config.effective_batch_size`).
Scanner сохраняет имена на один проход, а CachedNameReader хранит точные RGB → Identity
между проходами в ограниченном LRU. Числа и решения не кешируются.
`reader_factory` подключает `CacheStorage`: отдельные `data/name-cache/cpu.names`
и `dml.names` содержат только точные RGB NAME и Identity в порядке LRU.
При создании Reader проверяются формат, checksum и совместимость модели/обработки;
восстанавливаются последние записи в пределах выбранной ёмкости. Ошибка даёт пустой кеш.
Снимки формирует OCR-поток, один фоновый writer атомарно заменяет файл. Изменения
сохраняются примерно раз в минуту, включая паузу Runner; завершение задания и закрытие
принудительно сохраняют изменения и ждут writer. Подробности — [OCR](OCR.md#сохранение-name-кеша).
Пакет может содержать имена следующей группы. QTY и BUYOUT распознаются только после
сопоставления имени с правилом, до конца выбранной группы, не ниже неё.
Неоднозначные сокращённые имена и пересекающиеся правила отклоняются; fuzzy matching нет.
Неопределённое количество сохраняет свой статус, для расчёта используется 1.
Цена проверяется по лимиту лота, цене закупки за штуку и текущему бюджету;
прогноз прибыли после комиссии 5% должен быть положительным.

Tk работает в основном потоке. OCR и Runner выполняются в одном постоянном рабочем
потоке `OcrSession` (executor с одним worker); результаты передаются через очередь.
Reader создаётся при первом задании, явно прогревается до получения кадра и сохраняется
между заданиями до закрытия UI. Прогрев idempotent для каждого технического batch.
Смена CPU/GPU сохраняет кеш и закрывает старый Reader до создания нового;
новый Reader загружает совместимый файл выбранного устройства.
одновременно работает только одна NAME-сессия выбранного устройства. CPU-настройка
batch сохраняется, GPU использует 9 независимо от group_size. Числовой OCR остаётся CPU.
Перед первым созданием сессии UI импортирует native Tesseract в главном потоке:
установленная сборка cysignals регистрирует там обработчики сигналов Python.
Это не создание OCR API: его экземпляры и модели остаются на рабочем потоке.
Ошибка подготовки закрывает неисправный Reader; следующая попытка создаёт новый.
Ошибка обычного задания сохраняет подготовленный Reader. Desktop закрывается после
каждого задания. Стоп не выгружает OCR. Закрытие UI запрашивает стоп, ждёт завершения
работы, затем ставит освобождение Reader в тот же поток и опрашивает Future без
блокировки Tk. Новое задание нельзя запустить до обработки события завершения старого.
`SessionClock` измеряет монотонное время от Start/Replay до завершения задания,
включая подготовку и паузы. UI обновляет HH:MM:SS при опросе очереди; время окончания
берётся из события worker, поэтому задержка обработки очереди не увеличивает результат.
Редактирование правил и настроек блокируется
на время работы. Каталог загружается в RAM в начале запуска; бюджет читается
из SQLite. Соединения SQLite открываются на операции и не разделяются между потоками.

Перед запуском рабочего потока отдельный поток регистрирует F8/F9 через
`RegisterHotKey` с `MOD_NOREPEAT`. Он переносит `WM_HOTKEY` в очередь для Tk:
нажатие и отпускание между опросами UI не теряются. Ошибка регистрации блокирует
запуск, ошибка обработки очереди запрашивает стоп. После завершения обе регистрации
освобождаются. Пользователь подтвердил F8/F9 при активной игре 2026-10-15.

Режим по умолчанию — наблюдение: после задержки 3 секунды один захват и один
проход без кликов. Replay читает файл. Автопокупка запускается явным выбором
режима и требует непустого каталога без неразрешённых попыток.
Live mutex предотвращает одновременное управление игрой вторым экземпляром.

`Runner.run(..., probe=True)` — отдельный однопроходный режим проверки меню;
совместное включение live и probe запрещено. Он использует тот же Search,
сопоставление и перепроверки `purchase(..., probe=True)`, но завершает путь до
`begin_buy` и клика BUY. Диагностика хранится в `probe-UUID`, итог — в events,
attempts/бюджет не меняются. Меню остаётся открытым. При паузе/стопе режим завершается.

## Цикл автопокупки

1. Проверить чистый аукцион; перенести указатель на Search без нажатия,
   дождаться стабильных полей всех девяти строк, снять исходный кадр и нажать Search.
2. В changed сразу опрашивать поля, дождаться отличия и стабильности всех девяти
   строк; подтвердить полным чистым кадром. В static — задержка и один чистый кадр.
   UNCHANGED пропускает OCR/BUY и сразу повторяет Search; при нестабильности ожидание продлевается один раз.
3. Выбрать лучший допустимый лот первой подходящей группы. История UNKNOWN_RECOVERED не исключает кандидатов.
4. Открыть меню, при revalidate_lot один раз повторно прочитать лот, сравнить поля ещё одного кадра перед BUY.
5. Зафиксировать намерение в SQLite, отправить один BUY и наблюдать результат.
6. Записать результат и диагностику; восстановить чистый аукцион
   и перейти к следующему Search, если остановка или пауза не запрошены.

Фиксированная пауза после уведомления удалена. Старое поле `post_result_delay_ms`
игнорируется при загрузке JSON и больше не сохраняется. Вместо паузы проверяется экран.
Перед каждым Search (changed и static) `Desktop.move()` переносит обычный или
виртуальный указатель на кнопку. Исходный кадр для сравнения берётся только после
стабилизации NAME/QTY/BUYOUT всех девяти строк в течение `search_stable_ms`.
Это исключает снятие подсветки после OK из признаков обновления Search.
Стабильная пустая таблица не принимается сразу: ожидается появление ярких пикселей
в NAME (>100 хотя бы в одном RGB-канале, без OCR). После `settle_timeout_ms` стабильная
пустая таблица допускает Search, чтобы настоящий пустой результат не заблокировал поиск.
Непрерывные изменения до таймаута дают PRESEARCH_UNSTABLE без Search/OCR/BUY;
live повторяет подготовку, probe завершается. Это эвристика окончания отрисовки,
не подтверждение ответа сервера. Опрос подготовки использует `search_poll_ms`
(sleep не больше 10 мс; 0 — без sleep), пауза/стоп проверяются между захватами.
Следующий клик по подготовленной позиции повторно проверяет фокус/координаты/отмену,
но не повторяет MOVE и ожидание мыши. Обычные клики по другим позициям не меняются.
`prepare_move_ms`, `prepare_ms`, `prepare_sleep_ms` описывают подготовку; её захваты
и проверки входят в initial_capture_ms/initial_check_ms. prepare_ms включает эти
операции и не складывается с ними повторно. Показатели captures/first_change_ms/stable_ms
по-прежнему относятся только к фазе после Search.
Восстановление длится до 1 секунды: известное уведомление закрывается через OK,
у неизвестного стандартного окна координаты OK определяются по шаблону `modal_ok`.
Оставшееся меню покупки закрывается через Search. Разрешено до трёх кликов за
восстановление, с интервалом не менее 300 мс после завершения клика; каждый клик основан на новом кадре.
Пауза между проверками восстановления — 15 мс.
При чистом экране возврат немедленный. Неудача восстановления, потеря фокуса и
INSUFFICIENT останавливают ввод. Смена строки/лимита до BUY отменяет только кандидата,
восстанавливает экран и возвращает STALE; следующий live-цикл начинает новый Search.

Стабильность пикселей не доказывает получение свежего ответа сервера.
В changed фиксированная задержка не применяется. `FieldMonitor` берёт точные RGB
поля NAME/QTY/BUYOUT без таймеров; NumPy concatenate(axis=None) собирает их в один
компактный массив без отдельных crop().copy(). Не выполняются OCR, хеширование
и template matching на каждом промежуточном кадре. Контроль интерфейса нужен перед
Search, на финальном полном кадре и при таймауте перед повтором. Перед покупкой
остаются отдельные проверки. Повторная проверка того же кадра в run после fresh убрана.
Отдельный шаблон `modal_ok` блокирует стандартное центральное окно даже при
неизвестном тексте и видимом заголовке аукциона; он не определяет статус покупки.
Проверяется также перед BUY. Неизвестные окна другого оформления без этого
контрола могут не распознаваться: универсального детектора любых окон нет.

По умолчанию наблюдаются девять строк. Экспериментальный триггер четырёх строк
после первого отличия расширяется на девять. При отсутствии отличий к половине
таймаута он также расширяется на девять для обнаружения изменений нижних строк.
При расширении контроля новый Search не нажимается; готовность требует минимум двух
равных наблюдений всех полей в течение `search_stable_ms=30` мс. Окно отсчитывается
заново при каждом отличии. Оно сохраняется и при polling=0, чтобы не принять
два захвата одного отображённого игрового кадра. Полный кадр перед OCR сверяется
со всеми девятью полями и исходным списком. Изменившийся финальный кадр снова
запускает стабилизацию. Это не гарантия против произвольно поздних поэтапных обновлений.

Таймаут `settle_timeout_ms=800` считается после завершения клика. Если ни одного
изменения не замечено и финальный интерфейс чист, fresh возвращает None/UNCHANGED.
Live сразу повторяет Search без OCR, BUY и записи PNG; probe завершается NO_CHANGE.
Если изменение было, но список не стабилизировался (включая возврат к исходному),
ожидание один раз продлевается ещё на `settle_timeout_ms`, сохраняя контроль
стабильности. Если и этого недостаточно, UNSTABLE сохраняет диагностику, пропускает
OCR/BUY и разрешает следующий Search. Финальная проверка таймаута сравнивает все
девять строк; нестабильный кадр никогда не поступает в OCR. Если интерфейс после
Search пришлось восстановить, возвращается UI_RECOVERED без анализа старого кадра.
Probe при UNSTABLE/UI_RECOVERED завершается, live продолжает следующий цикл.

`search_poll_ms=5` задаёт только polling Search: 0 не вызывает sleep, 5 — быстрый,
30 — экономный режим. Захваты и OCR выполняются последовательно в одном worker.
Опрос меню/результата сохраняет прежние интервалы. Обязательный cycle_interval_ms
из live удалён; поле осталось в Config для совместимости со старыми файлами.
Региональный захват через Pillow bbox сохраняет глобальные координаты FieldMonitor;
полный RGB кадр для OCR и диагностик остаётся 1920×1080. Pillow сначала захватывает
весь экран внутри native API и затем обрезает: измеренный выигрыш относится к
дальнейшей конвертации и копированию, не к настоящему региональному GPU-захвату.
`search_mode=static` пропускает цикл сравнения: после search_wait_ms выполняются
один захват, проверка чистого списка и отмены. Результат трассы STATIC_DELAY не
означает подтверждённое обновление. Начальное ожидание применяется только в static
и отменяемо с шагом 20 мс; settle_timeout_ms применяется только в changed.

`revalidate_lot=False` пропускает единственный вызов Scanner.row после открытия меню и использует
исходное Decision. Экономика заново проверяется по текущему бюджету без OCR;
меню, финальное сравнение пикселей, BUY_SENT и обработка результата сохраняются.
Без повторного OCR замена лота до открытия меню может не обнаружиться.
Значение revalidate_lot сохраняется в detail покупки/probe. Старые JSON получают
changed/true по умолчанию; UI сохраняет переключатели, блокирует их на время работы.
Runner держит в памяти исходный/последний кадры и метаданные захватов одного
Search. В probe после scan сохраняются `search-UUID/before_search.png`, точный
вход OCR `screen.png` и `detail.json` с временами после отпускания кнопки,
признаками changed/stable/clean и фазами контроля. Хеши из горячего пути удалены;
до 128 наблюдений сохраняются в трассе (при превышении остаются первые 127 и последнее).
При UNSTABLE диагностика пишется перед пропуском цикла (последний кадр не использован OCR).
UNCHANGED и успешные live-циклы не пишут PNG
Search; предыдущая трасса заменяется в памяти при следующем fresh().
В режиме `click_mode=cursor` захват требует активного окна с заданной частью заголовка, занимающего основной
экран 1920×1080. Перед кликом фокус проверяется повторно. Replay также принимает
1920×1081 без масштабирования. Координаты интерфейса фиксированы.

Desktop переносит курсор через SetCursorPos, ждёт `mouse_move_wait_ms` (40 мс),
перепроверяет фокус и GetCursorPos, затем отдельно отправляет DOWN и UP через
SendInput с удержанием `mouse_button_hold_ms` (40 мс). К каждому интервалу
независимо применяется равномерный разброс `mouse_jitter_ms` (±10 мс), заново
для каждого клика; границы ограничены 10–1000 мс. jitter=0 отключает разброс.
UI предлагает исходные 40+40 ±10, 20+20 и экспериментальные 10+10 без разброса.
Проверка позиции относится
к указателю Windows, а не подтверждению обработки движения игрой. Ожидания
опрашивают паузу/стоп через 10 мс. До DOWN отмена выдаёт ScanCancelled; после
DOWN кнопка освобождается через finally, отмена сокращает удержание и позволяет
Runner наблюдать результат отправленного BUY. Ошибки ввода не повторяют DOWN;
ошибка после намерения BUY приводит к UNKNOWN. При ScanCancelled внутри клика
BUY до DOWN намерение завершается CANCELLED без списания бюджета.
Настройки мыши общие для проверки меню и автопокупки; реальная доставка после
этого изменения ещё требует проверки. [Наблюдения и тесты](../validation/input-qty-20261015/README.md).

`click_mode=background` выбирает BackgroundDesktop: он наследует захват, тайминги,
метрики и отмену Desktop, заменяя перенос/проверку указателя и DOWN/UP на
PostMessage (WM_MOUSEMOVE, WM_LBUTTONDOWN, WM_LBUTTONUP). Поле «Клики» сохраняется
в Config; старые настройки выбирают cursor. Изменение доступно между запусками.
Проверка доступности окна вместо фокуса ищет видимые несвёрнутые окна с нужным
заголовком: при наличии точных совпадений рассматривает только их, иначе — совпадения
по подстроке. Затем фильтрует по покрытию основного экрана и требует одного кандидата.
Закрепляет его HWND, полный заголовок, PID/TID. Перед/после захвата и
при клике проверяются существование, видимость, отсутствие сворачивания и
покрытие основного экрана 1920×1080 клиентской областью. Точное равенство размеров
не требуется: на машине пользователя измерено окно 1920×1081 с началом (0,0).
Первоначальная геометрия закрепляется; её изменение останавливает ввод.
Координаты переводятся ScreenToClient и проверяются по фактическому размеру клиента.
Новое окно автоматически не подхватывается; UP адресуется первоначальному HWND.
Фокус другого приложения допустим. ImageGrab продолжает читать основной экран:
игра должна быть видима и не перекрыта. Проверка IsWindowVisible не определяет
перекрытие другими окнами. Доставка сообщений не подтверждает их обработку игрой;
мини-скрипт подтверждён пользователем 2026-10-19, полный новый путь требует проверки в игре.

В обоих режимах первое распознавание кнопки BUY ещё не завершает ожидание меню:
выбранные NAME/QTY/BUYOUT должны точно совпадать в последовательных кадрах минимум
30 мс при непрерывно распознаваемом меню. Изменение пикселей или исчезновение меню
сбрасывает интервал; общий таймаут — 500 мс, пауза между проверками — 15 мс.
Затем выполняются повторный OCR (если включён) и строгая проверка свежего кадра перед BUY.
`purchase_timings` содержит `click_mode` и при отмене через skip_purchase — `skip_reason`.
Отмена на ожидании меню, несовпадении OCR или финальных пикселей в background сохраняет
`skipped-UUID/screen.png`, `detail.json` с исходным/проверенным решением; для финального
сравнения дополнительно `reference.png` и `changed_fields`. Ошибка записи диагностики
не разрешает BUY; причина остаётся в метриках. Анализ видео и ограничения вывода:
[разбор](../validation/background-video-20261019/README.md).

## Состояния попытки покупки

`Store.begin_buy()` транзакционно записывает `BUY_SENT` **до** отправки BUY.
Поэтому этот статус означает намерение: при сбое клик мог ещё не произойти.

| Следующее состояние | Последствия |
|---|---|
| `SUCCESS` | Ручной режим: списание цены в той же транзакции; OCR-режим: сверка фактического баланса |
| `UNAVAILABLE` | Ручной режим: бюджет не меняется; OCR-режим: проверка возврата средств перед следующим циклом |
| `UNKNOWN` | Результат не распознан; новые BUY запрещены до восстановления экрана |
| `UNKNOWN_RECOVERED` | Чистый экран подтверждён; резерв цены в бюджете, покупки разрешены после нового Search |
| `CANCELLED` | Отмена после записи намерения, но до отправки BUY |
| `INSUFFICIENT` | Шаблон текста недостатка денег; без списания, остановка, окно остаётся открытым, ручной разбор |
| `BALANCE_MISMATCH` | Изменение счёта не соответствует цене/уведомлению; расхождение записано в журнал, новый баланс сохранён, покупки продолжаются |

Незавершённый `BUY_SENT`, `UNKNOWN`, `INSUFFICIENT` и любая
попытка с `balance_pending=1` блокируют новую покупку. Завершённый BALANCE_MISMATCH
не входит в блокирующие статусы, включая записи прежних запусков. `balance_check`
сохраняет ожидаемый и фактический расход; такая попытка не добавляет прибыль SUCCESS.
В live после паузы или перезапуска UNKNOWN сначала проходит восстановление экрана.
При выключенном OCR баланса `Store.recover_unknown()` транзакционно переводит UNKNOWN в UNKNOWN_RECOVERED и
однократно уменьшает заданный локальный бюджет на возможную стоимость покупки.
Это резерв, не подтверждение успеха. Совпадение названия, цвета, заточки и полной
цены не является серверным ID: Scanner и Store не блокируют новые предложения
по истории UNKNOWN_RECOVERED. В режиме changed после UNKNOWN Runner требует нового Search с
изменившимся стабильным списком перед следующей покупкой; UNCHANGED, UNSTABLE,
отмена и восстановление интерфейса этот запрет не снимают. Повтор BUY в рамках
восстановления не отправляется. Сохраняются проверки строки/меню перед покупкой,
транзакционный запрет при неразрешённых состояниях/pending и уникальный id попытки.
Известное расхождение: static снимает этот барьер после задержки и чистого кадра,
не проверяя изменение списка; замечание A03 в [аудите](AUDIT_2026-10-20.md).
Ручная отметка переводит состояние в `MANUALLY_REVIEWED`, не объявляет успех и не
корректирует бюджет: при необходимости его исправляет пользователь. Повторная
финализация и повторное резервирование запрещены.

После BUY пауза/стоп не прерывают наблюдение результата до таймаута
`result_timeout_ms` (по умолчанию 1000 мс), с паузой опроса 40 мс. При запросе остановки/паузы окно
результата автоматически не закрывается. После продолжения бот восстанавливает
оставшееся меню или распознанное уведомление до нового Search.
Запрос проверяется повторно после последнего захвата/распознавания перед кликом OK.

## Данные и границы проверки

`Config.auto_balance=False` сохраняет ручной режим. При True `begin_buy` в одной
транзакции сохраняет `balance_before` и `balance_pending=1`. Наблюдённый результат
записывается без расчётного списания; CANCELLED/INSUFFICIENT снимают pending.
В остальных случаях pending блокирует следующий BUY, даже для SUCCESS, и не
позволяет скрыть запись очисткой истории. После восстановления чистого аукциона
Runner читает два одинаковых баланса на отдельных кадрах с паузой 150 мс;
общий предел чтения 2 секунды. После UNKNOWN/UNAVAILABLE перед чтением ждёт
700 мс, после SUCCESS — только при первоначальном расхождении и перед повторным чтением.
`reconcile_balance` атомарно записывает фактический бюджет, итоговый статус и
`balance_check` (до/после, ожидаемое/фактическое списание, исходный статус).
UNKNOWN без изменения становится UNAVAILABLE, с точным списанием — SUCCESS;
остальные изменения — BALANCE_MISMATCH. SUCCESS/UNAVAILABLE также сверяются.
Сохраняются кроп счёта `balance.png` и `balance_check.json`; отказ записи файлов не отменяет аудит в БД.

Пауза/стоп отменяют закрытие окна и чтение, но сохраняют pending. Следующий live
запуск/продолжение сначала завершает сверку с сохранённым исходным балансом.
Старый UNKNOWN без baseline нельзя автоматически разобрать в OCR-режиме;
pending нельзя обойти выключением настройки. Неразрешённый BUY_SENT всегда
требует ручного разбора, поскольку неизвестно, был ли отправлен клик.
Ручная отметка очищает pending, не объявляет успех и не меняет бюджет.
Наблюдение результата по балансу — эвристика: внешние поступления/траты могут
исказить вывод. Несовпадение записывается в журнал без остановки; цена предмета
не переписывается, дальнейшие лимиты проверяются по новому прочитанному балансу.

Баланс синхронизируется на старте live до бюджетного порога, после паузы и раз
в 60 секунд между циклами; сверка покупки сбрасывает этот таймер. Наблюдение
синхронизирует один раз; Replay/probe не меняют бюджет через OCR. Событие
`account_changed` обновляет бюджет и историю в Tk poll (100 мс); событие attempt
обновляет историю намерения/результата. Опрашивать SQLite каждые 100 мс не требуется.
История отображает целую часть с разрядными пробелами, хранит и сортирует точные значения.

Runner суммирует `Decision.profit` через Decimal только после сохранения SUCCESS
и завершения сверки (если она включена)
в текущем запуске. Сумма и число покупок передаются UI и пишутся в события
`session_profit`; новый запуск сбрасывает счётчик, пауза не сбрасывает.
Это прогноз продажи после комиссии 5%, а не реализованная прибыль.
В live заданный бюджет меньше 50 000 ₽ завершает запуск с `BUDGET_LIMIT`
(событие `budget_stop`): до первого ввода, перед Search, после покупки и после
резервирования UNKNOWN. Ровно 50 000 ₽ разрешено; None отключает порог.
Наблюдение, Replay и проверка меню не останавливаются по этому порогу.

`data/stalbot.sqlite3` содержит правила, историю, бюджет и события;
`data/settings.json` — настройки; `data/diagnostics/<attempt-id>/` — кадр и JSON
результата; `data/errors.log` — ошибки рабочего потока UI.
Store автоматически добавляет `rules.upgrade_max`, `attempts.hidden_from_history`,
`balance_before`, `balance_pending` и `balance_check`
в старую SQLite без изменения прежних значений и JSON попыток. Уникальный индекс
учитывает обе границы; одиночный уровень и диапазон с равными границами эквивалентны.
История фильтруется и сортируется в SQLite без ограничения числа записей по умолчанию;
необязательный `limit` остаётся для явных запросов API. Поиск кириллицы использует
casefold, числовые колонки — числовое сравнение. UI передаёт `local_dates=True`:
SQL-функция local_day переводит UTC timestamp в календарный день Windows через
datetime.astimezone, сохраняя микросекунды на границах дня. Таблица использует тот же
местный часовой пояс; хранение времени остаётся UTC. Календарь возвращает ISO-дату
в StringVar и сразу применяет фильтр; быстрые периоды используют местный date.today.
UI суммирует Decimal(profit) только у SUCCESS без balance_pending среди всех полученных строк,
без повторного вычета комиссии. Неуспешные/неопределённые/ручные статусы не дают прибыль.
Очистка помечает завершённые попытки
как скрытые, сохраняя аудит, бюджет и все защитные записи. Запросы unresolved
не зависят от видимости истории. UNKNOWN_RECOVERED сохраняется для аудита и сверки
резерва бюджета, без бессрочного запрета одинаковых предложений. Подробности загружаются по id попытки.
Replay не отправляет ввод в игру, но не является режимом без записи на диск:
CLI открывает/создаёт БД, а UI сохраняет настройки и событие Replay.

Scanner накапливает `name_ms/quantity_ms/buyout_ms/evaluation_ms/total_ms` заново
на каждый проход. `Decision.elapsed_ms` включает долю времени NAME-пакета и чтение строки;
оно не заменяет время всего анализа, поскольку пакет может предчитать лишние имена.
Runner и UI Replay добавляют время получения кадра, проверки экрана, чтения бюджета
(в Replay вместе с каталогом) и `decision_ms`. `elapsed_ms` события — только `scan.total_ms`.
`decision_ms` не включает загрузку моделей, стартовую задержку, сериализацию, очередь/отрисовку
UI, перепроверки и BUY. CLI выдаёт только стадии scan. Это основа будущих измерений,
не свидетельство ускорения или времени полного цикла покупки.

Контроллер покрыт тестами с имитацией Desktop; пользователь подтвердил наблюдение
на двух примерах с группой 1 ([источник](../validation/observation-user-20261015/README.md)).
Офлайн OCR и группы проверяются `tools/validate_bot.py` на знакомом датасете.
2026-10-15 пользователь подтвердил корректную работу полного цикла автопокупки
в игре. Это пользовательская проверка текущей реализации; ускоренные параметры
и все сочетания групп/критериев требуют отдельных измерений и проверки.
Распознаются SUCCESS, UNAVAILABLE и INSUFFICIENT; другие неизвестные уведомления
приводят к UNKNOWN. Для INSUFFICIENT используется отдельный текстовый шаблон,
при нескольких совпадениях детектор возвращает None, а не выбирает первый.

## Границы подробных метрик

`fresh()` сбрасывает `search_timings` на каждом проходе: initial_capture_ms,
initial_check_ms, click_ms, wait_ms (ноль в changed), captures_ms, checks_ms,
ui_checks_ms, poll_sleep_ms, число captures/comparisons, capture_avg_ms/capture_max_ms
и total_ms. checks_ms теперь только подготовка полей и сравнение; ui_checks_ms —
финальные шаблоны. comparisons считает сравнения массивов, не число ROI.
first_change_ms/stable_ms — время от завершения клика до наблюдаемого изменения
и окончательной готовности (None при отсутствии); это не серверное время.
unchanged_searches накопителен на экземпляр Runner. Начальный кадр не входит в captures. mouse внутри
содержит детализацию click_ms, а не дополнительную затрату. Измеряются реальные
интервалы perf_counter, не значения настройки sleep. Метаданные/сериализация могут
создавать остаток между суммой стадий и total_ms.

`Desktop.click()` возвращает started_at/down_sent_at/released_at в секундах
perf_counter и move_ms/hold_ms/total_ms. DOWN timestamp ставится после успешного
SendInput, UP — после отпускания. При ошибке полного результата click нет.
Эти абсолютные отсчёты нужны для разностей в процессе, не являются временем UTC.

`purchase_timings` начинается заново для каждой попытки: buy_call_ms перед вызовом
Desktop.click, buy_pressed_ms по down_sent_at, result_observed_ms после определения
известного результата, buy_to_result_ms — их разность. Origin cycle означает начало
текущего цикла до Search; прямой вызов purchase использует origin purchase.
При отсутствии факта нажатия/распознанного ответа соответствующие значения None.
UNKNOWN — не распознанный результат, поэтому result_observed_ms остаётся None.
ready_ms в probe означает завершение проверок, BUY не имитируется.

reread_ms — один повторный OCR после открытия меню (0 при off); selection_click_ms — клик лота;
menu_wait_ms включает захваты, шаблоны и паузы до меню; result_wait_ms — наблюдение
после завершения BUY-клика. captures_ms покупки — захваты вне циклов ожидания меню
и результата. purchase_total_ms включает последующую диагностику и восстановление
экрана; он не равен времени до распознавания ответа.
Финальное событие purchase_timing содержит метрики покупки и цикла/Search даже
при отмене/ошибке. Диагностика попытки содержит снимок метрик до записи файлов.
Накопительные milestones, итоговые времена и их вложенные части не суммируются.
