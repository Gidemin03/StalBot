# Постоянный прогрев OCR и проверка меню — 2026-10-15

## Изменения

- Reader UI создаётся и прогревается на одном постоянном потоке перед первым
  получением игрового кадра. Между Старт/Replay, циклами, остановками и паузами
  используется тот же экземпляр. Закрытие UI асинхронно освобождает его на потоке-владельце.
- NAME прогревается для технического batch 1/3/9 по необходимости; QTY/BUYOUT —
  однократно. Используются искусственные изображения в памяти. Подготовка вынесена
  из времени анализа; она показывается в UI и сохраняется отдельно.
- Первый импорт установленной сборки Tesseract вынесен в главный поток: её
  cysignals требует регистрации сигналов Python там. Это обнаружено реальным
  smoke-тестом, не поддельным Reader. Экземпляры OCR API создаются в рабочем потоке.
- У сокращённых имён upgrade=0 по прямому уточнению пользователя. Признак truncated
  сохраняется; покупка по сокращению всё ещё запрещена. Повреждённые суффиксы
  несокращённых имён не становятся +0. Dataset/labels не изменялись.
- Новый явный режим «Проверка меню (без BUY)»: один Search, выбор группы и
  перепроверки меню/лота, затем диагностика `probe-UUID` и завершение без BUY_SENT,
  BUY и списания бюджета. Меню остаётся открытым для пользователя.
- В DEVELOPMENT_PLAN добавлены эксперименты последовательной и параллельной
  обработки QTY/BUYOUT, NAME на CPU, настоящего batch и совместного CPU+GPU 3+3.

## Подтверждённые проверки

Полный suite `.\.venv-benchmark\Scripts\python.exe -m unittest discover -s tests -q`:
**89 тестов, OK, exit code 0**. Включает жизнь сессии, ошибки подготовки, повторное
использование, остановку/закрытие UI, native-import ordering, новое правило заточки,
14 fake-сценариев проверки меню/Search и прежние защиты покупки. Tk smoke использует
clipboard; каталоги и бюджеты тестов находятся во временных БД.

Полная OCR-регрессия финального кода:

```powershell
.\.venv-benchmark\Scripts\python.exe tools\validate_bot.py --dataset dataset --models benchmarks\models --output validation\integration-warm-probe-verified-20261015.json
```

**Integration regression passed, exit code 0.**
[Финальный JSON с хешами](integration-warm-probe-verified-20261015.json).
Baseline неизменён: NAME/цвет 170/170, QTY 53/54 видимых чисел и 169/170 расчётно,
BUYOUT 146/153 видимых цен и 158/170 по значениям/состояниям, опасных ошибок на
этом наборе 0. Старые batch-проверки и 306 групповых комбинаций проходят.
Первый успешный отчёт до поправки native import также сохранён:
[integration-warm-probe-20261015.json](integration-warm-probe-20261015.json).

Два настоящих UI Replay через App.work в одной сессии, без Tk-ввода и игры:
[warm-session-ui-20261015.json](warm-session-ui-20261015.json).
Создан один Reader, вторая подготовка имеет created=false/warmed=false, ответы
одинаковы, history пуста, model освобождена после close_async. Первая подготовка
моделей заняла около 1547 мс (1129 загрузка + 418 прогрев); повторная — около 0 мс.
Первоначальный импорт Python/native модулей до сессии не входит в эти значения.
NAME девяти строк после прогрева: около 243 и 250 мс. Это smoke-проверка механизма,
не сравнительный benchmark ускорения или гарантия задержки в игре.

Независимый review UI/CLI не обнаружил дефектов повторного использования,
раннего Stop и закрытия. Stop во время native-прогрева ждёт завершения текущего
вызова, после чего захват/игровые действия не начинаются.

Не хватает изображения уведомления о недостаточном балансе; оно по-прежнему UNKNOWN.

Постоянная сессия сохраняет загруженное/инициализированное состояние, но не
гарантирует одинаковую задержку после простоя: ширина текста и нагрузка различаются.
Фонового «подогрева» вычислениями нет. CPU/GPU и параллельные OCR-эксперименты пока
только запланированы; рабочих потоков распознавания по-прежнему один.
